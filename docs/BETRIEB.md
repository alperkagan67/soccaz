# Betrieb

Alles läuft mit Docker Compose: App, PostgreSQL, Caddy (HTTPS) und eine tägliche Sicherung. Kein Kubernetes.

## Erstinstallation (Server, z. B. Hetzner Cloud CX22)

1. Server mit Ubuntu 24.04, Docker und Docker Compose installieren, Domain per A-Record auf die Server-IP legen.
2. Repository klonen: `git clone https://github.com/alperkagan67/soccaz.git && cd soccaz`
3. Konfiguration anlegen: `cp .env.production.example .env` und alle Werte eintragen (Datenbankpasswort, Domain, `AUTH_SECRET`, Google, `JOB_SECRET`).
4. Starten: `docker compose up -d --build`
5. Prüfen: `https://deine-domain/api/health` liefert `{"status":"ok"}`.
6. Den ersten Admin festlegen (einmalig, nach der ersten Anmeldung):
   `docker compose exec db psql -U socaz -c "update users set role='admin' where email='deine@mail.de'"`

Die Migrationen laufen automatisch bei jedem Start (`migrate`-Dienst).

## Hallenliste

Die Datei `data/nrw-hallen-osm.json` enthält Soccer- und Fußballhallen in NRW aus OpenStreetMap (ODbL, ungeprüft). Einspielen (mehrfach ausführbar, überschreibt keine geprüften Hallen):

```
docker compose run --rm migrate node scripts/import-venues.mjs
```

Neu abrufen: `node scripts/fetch-venues-osm.mjs` (braucht Internet, dauert eine Minute). Im Admin-Bereich unter Hallen markierst du eine Halle als geprüft, sobald Buchbarkeit, Adresse und Preis stimmen. Geprüfte und Partnerhallen kommen im Veto zuerst.

## Überwachung

- **Fehler:** Sentry (`SENTRY_DSN` in der `.env`).
- **Erreichbarkeit:** Uptime Kuma als optionaler Dienst: `docker compose --profile monitoring up -d`. Er lauscht nur auf dem Server (Port 3001) und ist per SSH-Tunnel erreichbar: `ssh -L 3001:127.0.0.1:3001 <server>`. Beim ersten Öffnen Konto anlegen, dann einen HTTP-Monitor auf `https://<domain>/api/health` (Antwort `{"status":"ok"}`) und Benachrichtigung per E-Mail oder Telegram einrichten.
- **Geschäftszahlen** (Spiele, Umsatz, Guthaben, Auszahlungen) stehen im Admin-Bereich unter Finanzen. Prometheus und Grafana sind bewusst nicht dabei: Sie lohnen sich erst, wenn mehrere Server laufen.

## Betreiberangaben

Impressum und Datenschutzerklärung zeigen `OPERATOR_NAME`, `OPERATOR_ADDRESS` und `OPERATOR_EMAIL` aus der `.env`. Ohne diese Werte steht dort ein deutlicher Hinweis. Die Rechtstexte sind Entwürfe und müssen vor dem Start geprüft werden.

## Turniere und Veranstalter

Turniere dürfen nur freigeschaltete Veranstalter anlegen (Admin, Nutzer, „Als Turnier-Veranstalter freischalten“). Startgelder liegen bis zum Turnierende auf dem Konto `tournament`. Die Provision (Standard 10 Prozent) steht in der Tabelle `settings` unter `tournament_commission_percent`. **Turniere mit Preis laufen nur im Kartenmodell** (`card_payments_enabled` AN, Partnerhalle): es gibt kein Guthaben mehr; bei ausgeschaltetem Kartenschalter bleibt ein Turnier mit Preis in der Zahlungsphase stehen und wird in der Absagefrist abgesagt (nur Gratis-Turniere laufen weiter). Altgeld aus der früheren Guthaben-Zeit wird nicht ausgezahlt oder erstattet, sondern als `tournament.refund_skipped` / `tournament.settle_skipped` im Audit protokolliert (mit interner Spieler-ID, ohne Name/E-Mail); Admin 1 klärt es manuell.

## Monatsjob

Am 1. jedes Monats schreibt `close-city-challenge` den Vormonat der Stadt-Challenge fest. Er ist mehrfach ausführbar und wirkt nur einmal. Alle Jobs: `src/server/jobs.ts`.

## Google-Anmeldung einrichten

Google Cloud Console, Projekt anlegen, APIs und Dienste, Anmeldedaten, OAuth-Client-ID (Webanwendung).
Autorisierte Weiterleitungs-URI: `https://deine-domain/api/auth/callback/google`. Client-ID und Geheimnis in `.env`.

## Update

```
git pull
docker compose up -d --build
```

Rückgängig: `git checkout <vorheriger-commit>` und erneut `docker compose up -d --build`. Datenbankänderungen sind nur vorwärts, deshalb vorher sichern.

## Sicherung und Wiederherstellung

- Täglich 03:30 UTC erzeugt der Dienst `backup` eine Sicherung in `./backups` (14 Tage Aufbewahrung).
- Sofort sichern: `docker compose exec backup sh /backup-loop.sh once`
- **Monatlich testen:** `sh scripts/restore-test.sh` stellt die neueste Sicherung in einer Wegwerf-Datenbank wieder her und zählt Tabellen und Nutzer. Eine Sicherung ohne diesen Test gilt nicht als Sicherung.
- Sicherungen zusätzlich außerhalb des Servers ablegen (z. B. Hetzner Storage Box per `rsync` oder `rclone`).
- Wiederherstellen in die echte Datenbank: `gunzip -c backups/socaz-….sql.gz | docker compose exec -T db psql -U socaz -d socaz`

## Überwachung

| Stufe | Werkzeug | Einrichtung |
|---|---|---|
| Sofort | Uptime Kuma | eigener Container, Monitor auf `/api/health`, Benachrichtigung aufs Handy |
| Sofort | Fehlerprotokoll | `SENTRY_DSN` in `.env` setzen; ohne Wert gehen Fehler nur ins Containerprotokoll (`docker compose logs app`) |
| Bei echten Nutzern | Plausible | datenschutzfreundliche Statistik |
| Vor dem Geld-System | Prometheus und Grafana | Serverwerte, Alarme |

Geschäftszahlen (Spiele, Umsatz, Erstattungen) stehen im Admin-Dashboard, nicht in Grafana.

## Zeitplaner

Im Betrieb startet die App den Zeitplaner (pg-boss) selbst: Benachrichtigungen, Erinnerungen, automatische Absage, automatische Ergebnisbestätigung, Aufräumen. Einen Job von Hand anstoßen:

```
curl -X POST -H "x-job-secret: $JOB_SECRET" https://deine-domain/api/jobs/send-reminders
```

## Zahlungen einschalten

1. Rechtliches klären (Gewerbe, Steuer, AGB, Widerruf, Guthaben-Regeln). Siehe PLAN.md. Erst danach echtes Geld annehmen.
2. Stripe-Konto anlegen, Zahlungsmethoden (Karte, PayPal, SEPA) aktivieren.
3. In `.env`: `STRIPE_SECRET_KEY` eintragen; `STRIPE_CARD_WEBHOOK_SECRET` für den Kartenwebhook `https://deine-domain/api/stripe/webhook` (Ereignisse siehe unten). Der alte Aufladungs-Endpunkt `/api/webhooks/stripe` (`STRIPE_WEBHOOK_SECRET`) wird seit 012 M6b nicht mehr gebraucht: nicht neu anlegen; ein noch eingetragenes Ziel wird nur quittiert (siehe Betriebsbedingungen unten).
4. `docker compose up -d --build`, dann im Admin-Bereich unter **Einstellungen** den Zahlungsanbieter prüfen (muss "Stripe" zeigen) und **Zahlungen einschalten**.
5. Testen mit Stripe-Testschlüsseln (`sk_test_...`, Testkarte 4242 4242 4242 4242), bevor die Live-Schlüssel eingetragen werden.
6. Preise stehen unter **Hallen** (Standardpreise: 60 Minuten 80 Euro, 90 Minuten 110 Euro). Hallenkosten und Marge sind dort pro Regel einstellbar.

### Kartenzahlung (Vertrag 012, Stripe)

- Eigener Webhook-Endpunkt `https://deine-domain/api/stripe/webhook` im Stripe-Dashboard, **getrennt** vom alten `/api/webhooks/stripe`. Stripe vergibt je Endpunkt ein eigenes Signaturgeheimnis (`whsec_...`): das der alten Route steht in `STRIPE_WEBHOOK_SECRET`, das der neuen in `STRIPE_CARD_WEBHOOK_SECRET`. Nie dasselbe Geheimnis für beide eintragen. Ereignisse der neuen Route: `setup_intent.succeeded`, `setup_intent.setup_failed` (Karte hinterlegen) sowie `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.requires_action` und `charge.updated` (Abbuchung, M2; beim Ausrollen von 012 M2a im Dashboard zusätzlich anmelden, sonst kommen keine Abbuchungsergebnisse an); später `charge.dispute.*`. Verspätete oder doppelte Ereignisse sind unkritisch (Idempotenz über `stripe_events`). Die alte Route `/api/webhooks/stripe` (Guthaben) entfällt mit 012 M6.
- Weitere Variablen: `STRIPE_SECRET_KEY` (gemeinsam) und `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`. **`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` wird beim BAUEN in den Browser-Code eingebettet** (Dockerfile `ARG`, `docker-compose.yml` `build.args`, Wert aus der `.env`); `env_file` allein reicht nicht. Nach jeder Änderung des Werts neu bauen: `docker compose up -d --build`. Ohne Wert zeigt die Lobby kein Kartenformular. `pk_` und `sk_` müssen aus demselben Modus stammen (Test: `pk_test_`/`sk_test_`; Live: `pk_live_`/`sk_live_`); Staging nie mit Live-Schlüsseln bauen.
- **Worktrees und Stripe-Testschlüssel:** Der Nutzer trägt `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` und `STRIPE_CARD_WEBHOOK_SECRET` in `.env.local` ein (Testschlüssel, nie Live). `worktree.mjs` kopiert `.env.local` nur beim ANLEGEN eines Worktrees: Bestehende Worktrees bekommen neue Schlüssel nicht automatisch (Worktree neu anlegen oder `.env.local` selbst abgleichen). Worker-Apps brauchen `stripe listen --forward-to localhost:<Port>/api/stripe/webhook` (Port des Workers 3101-3104) mit eigenem Webhook-Secret (`whsec_...`, aus der Ausgabe von `stripe listen`, nur in der eigenen `.env.local`). Agenten lesen und geben `.env*` nie aus.

- **Kartenmodell einschalten (Go-live-Schritt):** `card_payments_enabled` nur ohne offene bezahlte Spiele umlegen; bezahlte Spiele bleiben im Guthaben-Modell bis zum Ende. Technisch gilt das Kartenmodell nur für Spiele der Frist-Regel, in denen kein Platz `paid_cents > 0` hat; Erstattung bei Austritt, Neuberechnung und Fixieren laufen für Spiele mit bezahlten Plätzen unverändert über das Guthaben. Altspiele und Turniere bleiben beim Guthaben.
- **Abbuchung (M2):** Die Ereignisse stehen im ersten Punkt. Abgebucht wird je Spieler der fixierte Anteil, mindestens 0,50 EUR (Überschuss bleibt in revenue); kostenlose Spiele werden nicht abgebucht. **`card_payments_enabled` darf in Produktion erst nach M3 (Nachzahlfenster, Nachrücker, Erstattung) und M4 (Dispute, DSGVO, E2E im Testmodus) eingeschaltet werden, und zwar erst, wenn M3c-1 (Fenster und Wiederabbuchen), M3c-1c (3-D-Secure-Freigabe) UND M3c-2 (Nachrücker, automatische Absage) gemergt UND deployt sind:** bis dahin bleibt ein Spiel mit fehlgeschlagener Abbuchung unabgerechnet, es hängt nach dem Ende des Fensters, `requires_action` bleibt eine Sackgasse, und es gibt keine Rückerstattung (siehe GO-LIVE-AUDIT G8-012/G9-012).
- **Absage mit Erstattung (M3a):** Hat ein Spiel Abbuchungszeilen, sagt nur **Admin 1** ab (`adminCancelMatch` / `adminCancelMatchAction`; der Captain nur vor der ersten Abbuchung). Die Absage wird angefordert (`matches.cancel_requested_at`), ab dann wird nichts mehr abgebucht oder abgerechnet; jede erfolgreiche Abbuchung wird voll auf die Karte erstattet (Tabelle `payment_refunds`, eine Zeile je Abbuchung, fester Schlüssel `refund:<Zeile>`, Hauptbuch Soll `revenue`, Haben `clearing`; **die Stripe-Gebühr der Abbuchung bleibt bei Soccaz und wird nicht zurückgebucht**). Erst wenn alle Erstattungen erfolgreich und keine Abbuchung mehr offen ist, wird das Spiel `cancelled`. Gelingt eine Abbuchung erst nach der Anforderung, wird sie sofort erstattet. Abbuchungen mit unbekanntem Ausgang werden vor dem Abschluss per Stripe-Suche (Metadaten) gesucht; ein Treffer wird verbucht und erstattet, kein Treffer (nach 5 Minuten) bleibt Audit `charge.search_empty` + Alarm, das Spiel bleibt "Absage angefordert". Job `card-refunds` (alle 5 Minuten) bringt angeforderte Absagen weiter. Webhook-Ereignisse zusätzlich anmelden: `refund.created`, `refund.updated`, `refund.failed` (und `charge.refund.updated`, `charge.refunded` werden nur vermerkt). **Alarm für Admin 1** (`getRefundAlerts` in `finance.ts`): fehlgeschlagene Erstattungen (z. B. `charge_disputed`: manuell über Stripe klären), Erstattungen mit unbekanntem Ausgang, Absagen länger als 1 Stunde offen, Abbuchungen mit unbekanntem Ausgang. Eine fehlgeschlagene Erstattung wird nie automatisch wiederholt.
- **Ausnahme-Erstattung auf die Karte (012 M6b 1c-iii b1, keine Migration):** Admin mit Rolle `finance` erstattet auf der Finanzseite des Spiels die GANZE Abbuchung eines Spielers (bei Übernahme dem Zahler); Teilbeträge gibt es noch nicht (Backlog 191). Die Erstattung geht als Stripe-Refund über `payment_refunds`; im Hauptbuch wird erst mit der Stripe-Bestätigung zurückgebucht. Die Meldung „Erstattung angefordert“ heißt nicht „erstattet“. Lehnt Stripe ab, bleibt die Zeile `failed`, Admin 1 bekommt den Alarm; die Zeile blockiert die Absage des Spiels und einen zweiten Versuch, bis Backlog 192 (Neuversuch oder Freigabe durch Admin 1) gebaut ist: bis dahin klärt Admin 1 den Fall manuell mit dem Stripe-Dashboard. Bei einem offenen oder verlorenen Zahlungsstreit zur Abbuchung lehnt die Aktion ab (erst den Streit klären).
- **Auslöser (M2b-2):** Der Job `card-charges` (alle 5 Minuten, unabhängig von `payments_enabled`) bucht Kartenspiele ab, sobald beide Captains bereit sind und die Frist erreicht ist (48 Stunden vor Anstoß, ggf. mit Karenz); bei weniger als 48 Stunden Vorlauf sofort nach dem zweiten Bereit (zusätzlich ohne Wartezeit aus `finalConfirm`, fehlgeschlagen holt der Job nach). Er bucht auch fehlende Stripe-Gebühren nach. Sobald Abbuchungszeilen existieren, sind Beitritt, Austritt, Rauswurf, Einteilung und **jede Absage (auch durch Admin oder Job) gesperrt** (Meldung: Abbuchung begonnen, bitte Support kontaktieren; einen Admin-Pfad gibt es bis M3 nicht), ebenso Bereit ändern, Ort ändern, Teams zusammenführen und Konto löschen: Erstattung auf die Karte gibt es erst mit M3. **Betriebsrisiko:** Nach dem Anstoß verarbeitet der Job die Zeilen nicht mehr; offene Zeilen (`pending`/`requires_action`) werden je Zeile einmal mit Audit `charge.after_start` markiert (nie erneut gesendet); `failure_code` wird dabei nur gesetzt, wenn er leer ist (ein vorhandener Code wie `authentication_required` bleibt und steht im Audit-Detail `previousCode`). Dann ist die Halle gebucht, aber nicht (voll) eingezogen, und es gibt noch keine Admin-Sicht oder Auflösung (M3/009): Audit und Zeilen manuell prüfen (GO-LIVE-Betriebsrisiko). Zeilen mit unbekanntem Ausgang (`failure_code = unknown_outcome`, Status `pending`, Audit `charge.unknown_outcome`) werden nie erneut gesendet und nie automatisch auf `failed` gesetzt; sie sind manuell bzw. per M3 über die Stripe-Suche aufzulösen. Ein Idempotenz-Konflikt (`idempotency_mismatch`) setzt die Zeile auf `failed`.
- **Nachzahlfenster und Wiederabbuchen (M3c-1, Migration 0039):** Scheitert eine Abbuchung an der Karte (Stripe-Kartencode, `authentication_required`, `no_payment_method`), beginnt das Fenster: `payment_charges.grace_until` = min(2 Stunden ab dem Fehler, Anstoß minus 1 Stunde), immer gesetzt (bei höchstens 1 Stunde Restzeit ist das Ende der Fehlzeitpunkt, also kein Fenster; NULL bedeutet nie ein Kartenproblem oder Altzeile vor Migration 0039). Geprüft wird immer das effektive Ende min(`grace_until`, Anstoß minus 1 Stunde). Ändert der Spieler im Fenster seine Karte (Lobby oder Konto), wird der Platz wieder `card_ready` und sofort neu abgebucht (`retryChargesInWindow`, auch im Job `card-charges` alle 5 Minuten): neuer Versuch mit Schlüssel `charge:<Spiel>:<Nutzer>:<n>`; vorher werden die bekannten PaymentIntents per `retrieve` geprüft (erfolgreich: verbuchen statt neu senden; offen: abbrechen; `processing`: Runde auslassen). Abgeschlossene Versuche stehen in `payment_charge_attempts` (Historie), die Zeile in `payment_charges` ist immer der laufende Versuch. Der Webhook `setup_intent.succeeded` ruft `retryChargesInWindow` bewusst **synchron nach der Transaktion** auf (sofortige Abbuchung nach „Karte ändern“; kostet Stripe-Latenz im Webhook-Request, Fehler sind isoliert). Der Job `card-charges` (`runCardCharges`, nur bei eingeschaltetem Kartenmodell) ruft `retryChargesInWindow` auf und holt so nach, was der Webhook-Pfad nicht geschafft hat (Stripe-Fehler, Abbruch); Altzeilen (`grace_until` NULL) werden nie angefasst, ein veralteter Lauf bricht nie den PaymentIntent eines neueren Versuchs ab (Berechtigung und Versuchsnummer werden vor dem Netzaufruf frisch gelesen). **Bekannter Restfall:** ändert sich der Zustand zwischen dieser Prüfung und der Drehung in `rotateAttempt` (Millisekunden, z. B. paralleles Fensterende), kann eine Zeile `requires_action` mit abgebrochenem PaymentIntent stehen bleiben; sie läuft mit dem Fenster aus und wird in M3c-2 behandelt. Technische Zustände (`idempotency_mismatch`, `unknown_outcome`, `after_start`) bekommen kein Fenster und keine Spielerbenachrichtigung; Altzeilen und `idempotency_mismatch` stehen im Admin-Alarm (`getRefundAlerts`: `legacyFailed`, `idempotencyMismatches`, `duplicateSuccesses`) zur manuellen Entscheidung. **Rollback Migration 0039:** erst den Code zurückrollen, dann `drop table payment_charge_attempts; alter table payment_charges drop column grace_until, drop column current_attempt;` (rein additiv, nichts anderes hängt davon ab, solange der alte Code läuft). **`card_payments_enabled` bleibt AUS**, bis M3c-1, die 3-D-Secure-Freigabe (M3c-1c) und der Nachrücker/die Auto-Absage (M3c-2) deployt sind; ohne sie bleibt ein Spiel nach dem Fensterende hängen und `requires_action` eine Sackgasse. Hinweis für Integrationstests: `.env.local` darf keinen `STRIPE_SECRET_KEY` enthalten, sonst bucht die Gebührenbuchung ohne Nutzer und das Aufräumen scheitert am Fremdschlüssel.

Die Abbuchungsprüfung liest den Zugang live (Zugang jetzt aktiv und keine Zusage: nicht abbuchbar), und wird ein Zugang während `payment` wirksam, bekommt das Turnier die Zusagepflicht und die Zugangsinhaber werden benachrichtigt. **Bei einem Turnier, das festhängt:** Admin 1 sagt es ab. **Notabschaltung (Kartenmodell AUS):** Frist- und Fensterjob sagen nicht ab; ein Turnier, bei dem sonst gehandelt worden wäre, bleibt in `payment`. Ab 6 Stunden danach bekommt Admin 1 eine Mitteilung (ohne Personendaten), danach alle 12 Stunden erneut, und der Alarm `card:tournament-frozen` steht in der Alarmliste, bis das Kartenmodell wieder AN ist oder das Turnier abgesagt wurde. Es gibt **keine** automatische Absage. **Betriebsrisiko:** ein Zugang, der kurz vor der Frist erteilt wird, macht ein Turnier zusagepflichtig (die Inhaber werden benachrichtigt); ein Zugang nach der Frist nicht mehr. Entzug nach dem Fixieren ohne neuen Inhaber: Absage zur Frist ohne Abbuchung. **Zahlung ohne Zuordnung:** eine erfolgreiche Stripe-Zahlung, die keiner Abbuchung zugeordnet werden kann, löst sofort eine Mitteilung an Admin 1 und den Alarm `card:unmatched-success` aus (im Stripe-Dashboard prüfen, gegebenenfalls erstatten); andere unbekannte Ereignisse zählen nur und alarmieren (`card:unmatched-events`) ab mehr als 5 in 24 Stunden. **Zusage der Halle (M5-7b):** der Betreiber sagt ein Turnier in `/halle` im Namen der Halle zu (verbindlich, mit Bestätigungsschritt); der **Abbuchungslauf nimmt die Zusage bis zu 5 Minuten später auf** (Takt des Jobs). Nicht-Zusage führt zur Absage zur Frist; Erinnerung an Veranstalter und Captains 24 h und 6 h vorher. **Altbestand prüfen vor dem Einschalten:** `node --env-file=.env.local scripts/report-tournaments-venue-access.mjs` (nur lesend, ohne Personendaten) nennt Turniere im Kartenmodell, deren Halle schon einen Zugang hat.
- **3-D-Secure-Freigabe (M3c-1c, AC-7, keine Migration):** Verlangt die Bank für einen Versuch eine Freigabe (`requires_action`, Code `authentication_required`), sieht der Betroffene in der Lobby den Knopf „Zahlung freigeben“ (im Konto unter „Offene Freigaben“ nur ein Link). Die Server-Aktion `createAuthorizationAction` liefert NUR ihm das `clientSecret` des laufenden Versuchs (Bedingungen: Kartenmodell AN, Spiel offen, Zeile `requires_action`, Fenster läuft; bei Stripe nochmals `requires_action` mit passendem Betrag/EUR/Kunde; höchstens 10 Herausgaben je Nutzer und Stunde; Audit `charge.authorization_requested` ohne Secret). Stripe.js (`handleNextAction`) schließt die Prüfung im Browser ab; das Ergebnis dort bucht NICHTS, gebucht wird allein über den Webhook (`payment_intent.succeeded` / `payment_failed` → `applyChargeInTx`). Scheitert die Prüfung, wird die Zeile `failed` im Fenster („Karte ändern“, Wiederabbuchen); läuft das Fenster ab, wird ein offener PaymentIntent abgebrochen und der Platz vergeben (M3c-2). Content-Security-Policy erlaubt `js.stripe.com` und `hooks.stripe.com` bereits (`src/lib/csp.ts`). Das Secret steht nur in der POST-Antwort der Server-Aktion (nie in Seite, RSC-Payload, URL, Log). Tests/CI: mit `PAYMENTS_FAKE=1` gibt es stattdessen zwei Test-Knöpfe, die ein signiertes Fake-Webhook-Ereignis auslösen (derselbe Weg). Ohne diese Freigabe wäre `requires_action` eine Sackgasse: `card_payments_enabled` bleibt AUS, bis M3c-1, M3c-1c und M3c-2 deployt sind.
- **Nachrücker: Alter und Einrichtung (R-T183):** Kandidaten der Warteliste brauchen `onboarded_at` UND `age_confirmed_at` (Alterspruefung beim Onboarding, `MIN_AGE`) zusätzlich zum Beitritts-Gate. Plattform-Mitarbeiter (`ensureStaffOnboarded`: Admin, Finanzen, Buchung, Moderation) bekommen `onboarded_at` ohne Alterspruefung, haben aber kein `age_confirmed_at` und spielen nicht mit; sie sind nie Nachrücker. Der Nachrücker rückt in das Team des ersetzten Platzes (`slot_team_id`, Heim oder Auswärts); die neutrale Nachricht „Kader geändert“ geht an die Captains genau dieses Teams.
- **Konto-Löschung bei laufender Abbuchung (DSGVO Art. 17):** Hat ein offenes Spiel (`lobby`/`confirmed`) des Nutzers Abbuchungszeilen, lehnt `deleteAccount` ab ("Bitte wende dich an den Support; die Löschung wird nach Klärung der Abbuchung durchgeführt"). Die Zeilen bleiben bis M3 offen, das Spiel wird nie automatisch abgesagt; die Löschung läuft deshalb **manuell über den Support**, sobald die Abbuchung geklärt ist (Zeilen terminal oder erstattet). Zahlungsnachweise (Belege, Hauptbuch, Abbuchungszeilen) bleiben nach Handels- und Steuerrecht aufbewahrt, die Löschung anonymisiert nur personenbezogene Angaben (Frist: unverzüglich nach Klärung, spätestens innerhalb eines Monats). Nur relevant, solange `card_payments_enabled` AN ist; der Schalter geht in Produktion erst nach M3/M4 an.
- **Bekannter Rest-Zyklus (sehr eng):** `mergeTeams` sperrt Team -> Spiele, `deleteAccount` Spiel -> Team (archiviert das Team, wenn der Löschende dessen einziger Admin ohne Mitglieder ist). Treffen beide im selben Moment dasselbe Team, bricht Postgres eine der Transaktionen ab (Deadlock-Erkennung); nichts wird beschädigt, die Aktion lässt sich wiederholen.
- `PAYMENTS_FAKE` darf in Staging und Produktion nie gesetzt sein (nur Tests/CI). In Produktion mit `PAYMENTS_FAKE=1` bricht die Kartenzahlung mit einem harten Fehler ab. Ohne Stripe-Schlüssel und ohne `PAYMENTS_FAKE` ist die Kartenzahlung ausgeschaltet (Webhook antwortet 503).

Hinweise: Das Buchungsjournal ist unveränderlich (Datenbank-Trigger). Korrekturen sind Gegenbuchungen. Die Zahlungsgebühr wird beim Verbuchen **geschätzt** (Einstellung oben); die echten Gebühren stehen im Stripe-Dashboard und sollten monatlich abgeglichen werden.

**Karenz (Entscheid t2q/t2s, engere Regel nach Review):** Eine Frist oder ein Nachzahlfenster, die **während der Pause** ablief (nach dem Ausschalten, bis zum Wiedereinschalten: Audit `card_switch.off`/`card_switch.on`), gilt frühestens **2 Stunden nach dem Wiedereinschalten** als fällig. Fristen VOR der Pause und Fristen NACH dem Wiedereinschalten bleiben unberührt (kein Wiederaufleben alter Fenster). **Mehrere Pausen (Flattern des Schalters):** für jede Frist D zählt jede Pause k mit Ausschalten_k < D <= Einschalten_k; die Karenz ist das späteste dieser Karenzenden (Einschalten_k + 2 Stunden), gedeckelt wie unten; eine spätere Pause, in die D nicht fiel, ändert nichts (Definition in TypeScript und SQL, Paritätstest; berücksichtigt werden die Pausen der letzten 14 Tage, höchstens 10). (a) Spiel-Frist `closeLobbiesAtDeadline`, (b) Turnier-Frist `closeTournamentsAtDeadline`, (c) Nachzahlfenster (AC-9, Spiele und Turniere: Nachrücker, Wiederabbuchen, 3-D-Secure, Anzeige) werden gleich behandelt (eine Regel, TypeScript und SQL, Paritätstest). Die Karenz wird **unter der Spiel-/Turniersperre frisch gelesen**: schaltet der Admin während eines Laufs ein, gilt sie trotzdem. **Grenzen:** (1) Die Karenz reicht nie über den Anstoß (Spiele, Turniere: Start) hinaus; reicht sie bis dahin, gilt die bestehende Absageregel mit **Klartext** ("Die Bezahlung war pausiert, … Die Erstattung folgt") und Erstattung, nie eine stille Absage (Absicht: die Halle ist gebucht, Notbremse vor dem Anstoß). (2) Bei Nachzahlfenstern endet die Karenz spätestens bei Anstoß minus 1 Stunde: liegt Wiedereinschalten + 2 Stunden danach, gibt der Nachrücker-Lauf den Platz direkt nach dem Wiedereinschalten frei. (3) Ohne beide Audit-Einträge (Seed, SQL ohne Eintrag) keine Karenz und keine Mitteilung (sichere Richtung). **Mitteilung** (`pause-notify.ts`): nach dem Wiedereinschalten (nach dem Commit, best effort; Rest über den 5-Minuten-Job `card-charges`, höchstens 200 Spiele/Turniere je Aufruf) bekommen NUR Spieler **ohne** hinterlegte Karte, die Captains ihrer Teams und (Turnier) der Veranstalter "Bezahlung ist wieder möglich, neue Frist: <Zeit>" (Typ `payment`, Berliner Zeit, ohne Namen Dritter). Nur für Spiele/Turniere im Kartenmodell, mit Preis, nicht abrechnungsgebunden und ohne Abbuchungszeilen, deren Frist in der Pause ablief und durch die Karenz verschoben wird; je Spiel/Turnier und neuer Frist genau einmal (Spiele: `reminders_sent`-Schlüssel `pause-resume:<neue Frist>`, Turniere: Marker `pause_notified:<Turnier>:<neue Frist>` in `settings`, atomar; die Marker bleiben stehen, wenige Bytes: ein späteres Aufräumen ist als Backlog-Zeile notiert). Ein fixierter Anteil (abrechnungsgebunden) schließt die Mitteilung NICHT aus: bei eingeschalteten Zahlungen gilt die Karenz auch dort (nur Abbuchungszeilen oder Gratis schließen aus). Die Kandidatenmenge ist per SQL auf Spiele/Turniere begrenzt, deren Anstoß/Start im möglichen Fristfenster der Pause liegt. **Alarm `card:tournament-stuck`** (Alarmliste, Admin 1+2): ein Turnier in der Zahlungsphase mit Preis, dessen Start vorbei ist (z. B. in der Pause eingefroren und nie wieder angefasst); keine automatische Absage, Admin 1 sagt ab, die Erstattung läuft automatisch.

### Notabschaltung Kartenzahlung (Admin 1, `/admin/einstellungen`)

> **Benutzbar ab dem Merge des Fixes „Pause: Frist-Job sagt nicht ab“ (PR-Nummer trägt w4 nach).** Vorher den Notschalter in Produktion nicht benutzen: Der Frist-Job konnte bei Zahlungen AN + Karte AUS Spiele absagen. Mit dem Fix gilt: in der Pause keine Absage, nach dem Wiedereinschalten 2 Stunden Karenz (Zeilen 1 und Annahme der Tabelle „Jobs und Schalter-Zustand“).

- **Nur Admin 1** (nicht Admin 2, nicht finance) schaltet `card_payments_enabled` in den Einstellungen: Abschnitt "Notabschaltung Kartenzahlung" zeigt den Zustand und seit wann (Zeitpunkt der letzten Änderung; ohne Zeile "Standard, noch nie geschaltet" = AUS). Ausschalten UND Wiedereinschalten verlangen einen **Grund** (3 bis 200 Zeichen) und das **Häkchen "Folgen gelesen"** (serverseitig geprüft), laufen in einer Transaktion unter Sperre und sind protokolliert: Eingriffsprotokoll `card_switch.off`/`card_switch.on` mit vorher/nachher, Grund im Klartext UND SHA-256 des Grundes (ohne Personendaten); die Einstellung trägt `updated_by`/`updated_at`. Beweisprotokoll nach 009: kein eigener Trigger (Entscheid t2s: ein Schalter, kein Overkill).
- **Wann schalten wir ab, und wer entscheidet:** Kriterien: (a) Stripe-Störung oder Webhook-Ausfall (Zahlungen kommen nicht an oder doppelt), (b) Fehlbuchungen (falsche Beträge, doppelte Abbuchungen), (c) Missbrauchsverdacht (gestohlene Karten, auffällige Zahlungsstreite), (d) defekter oder kompromittierter Schlüssel. Es entscheidet **Admin 1** (der Betreiber der Plattform); im Zweifel zuerst abschalten und danach klären (das Abschalten verliert kein Geld: bestehende Abbuchungen und Erstattungen laufen weiter, siehe Folgen). Das Wiedereinschalten entscheidet ebenfalls Admin 1, erst nach der Checkliste unten.
- **Ist Admin 1 nicht erreichbar (SQL-Eingriff):** Nur wer Schreibzugriff auf die Datenbank hat (Rolle `soccaz_owner`, Betreiber/Infrastruktur laut G25-009), darf das tun; der Eingriff wird mit dem Nutzer abgestimmt und ist die Ausnahme. Genaues Statement (ein **Boolean**, kein Text: ein String würde bei jedem späteren Umschalten in der Oberfläche die Meldung "von jemand anderem geändert" auslösen, weil der Vergleich den JSON-Wert prüft):
  `update settings set value = 'false'::jsonb, updated_at = now(), updated_by = '<ID von Admin 1>' where key = 'card_payments_enabled';`
  PLUS ein **handschriftlicher Eintrag im `audit_log`** (Aktion `card_switch.off`, Entität `setting`, `card_payments_enabled`; `before` mit dem alten Wert, `after` mit `value: false`, dem Grund im Klartext und dessen SHA-256 `reasonSha256`, wie die Oberfläche ihn schreibt; ohne Personendaten). Der Alarm `card:switch-off` ergibt sich allein aus dem Wert (Zahlungen AN und Karte AUS), es ist nichts weiter zu setzen. Wiedereinschalten per SQL analog mit `true` und `card_switch.on`. **Die Karenz braucht BEIDE Audit-Einträge: `card_switch.off` beim Abschalten UND `card_switch.on` beim Wiedereinschalten** (Entität `setting`, `entity_id` `card_payments_enabled`, `at` = der tatsächliche Zeitpunkt). Fehlt einer von beiden (SQL ohne Eintrag), gibt es keine Karenz und keine Mitteilung: die Spiel-Frist gilt sofort wieder und kann Spiele absagen. Bei einem SQL-Eingriff also beide Einträge von Hand schreiben.
- **Folgen AUS (Entscheid D): Zahlungen AN + Karte AUS = pausiert.** *Belegt (Code gelesen und getestet):* nichts wird kostenlos oder vom Guthaben gebucht; Beitritt bleibt möglich, "Bereit" ist gesperrt ("Bitte zahle zuerst deinen Anteil … melde dich beim Support", der neutrale Text kommt mit 1c-ii-b); Turniere zeigen "Zahlungen sind gerade pausiert", frieren ein (Alarm `card:tournament-frozen` ab 6 Stunden); `/admin/finanzen` zeigt `card:switch-off`, solange Zahlungen AN und Karte AUS sind (bei Zahlungen AUS = Gratis kein Alarm); bestehende bezahlte Plätze bleiben.
  *Steht still, solange die Karte AUS ist* (hängt an `cardModeActive`): die Abbuchung selbst (`charge-run`: "not_card_mode"), die Wiederabbuchung fehlgeschlagener Zeilen (`charge-retry`), das Übernehmen eines Anteils und dessen Ansicht (`cover`, `cover-view`), damit auch das Nachrücken über diese Pfade. *Läuft weiter:* Erstattungen und Absagen mit bereits abgebuchtem Geld (`refund.ts` prüft den Schalter nicht).
  *Belegt mit dem Fix (Test `payments-pause.test.ts`):* (1) Der Frist-Job `closeLobbiesAtDeadline` überspringt Spiele bei Zahlungen AN + Karte AUS (keine Absage, kein Buchen; Ausnahme: Spiele mit Guthaben im Platz, Altmodell, bis 1c-ii-b); Spiele MIT Abbuchungszeilen sagt er nie ab. (2) Nachzahl- und Übernahme-Fristen (AC-9): `runSubstitutes`, Wiederabbuchung und Übernehmen stehen in der Pause still (kein Platz wird frei, keine Absage); Kartenhinterlegung ist in der Pause ebenfalls gesperrt (`card-setup`): Spieler können vor dem Wiedereinschalten nichts nachholen. (3) `payShare` ist in der Pause gesperrt ("Zahlungen sind gerade pausiert", nichts gebucht); Ausnahme wie beim Frist-Job: Spiele mit Guthaben im Platz (`paid_cents > 0`) bleiben im alten Pfad, damit der Zweite zahlen kann und die Absage nicht erzwungen wird. (4) Die Karenz nach dem Wiedereinschalten wirkt nur mit BEIDEN Audit-Einträgen `card_switch.off` und `card_switch.on` (eine vollständige Pause); ohne (Seed oder SQL ohne Einträge) gibt es keine Karenz und es gilt sofort die reguläre Absage (sichere Richtung). Das Eingriffsprotokoll beim SQL-Ausschalten und -Wiedereinschalten ist daher Pflicht.
- **Wiedereinschalten, Checkliste (in dieser Reihenfolge, Grund und Häkchen wie beim Ausschalten):**
  1. Webhook-Zustellung im Stripe-Dashboard grün (letzte Ereignisse zugestellt, keine Wiederholungsstapel).
  2. Schlüssel und Modus stimmen (live oder test passend zur Umgebung; Schlüssel nicht ersetzt oder gesperrt).
  3. Offene Karten-Fälle und fehlgeschlagene Abbuchungen auf `/admin/finanzen` gesichtet und geklärt.
  4. Notiert: Zahl der eingefrorenen Turniere und der Spiele mit fälligen Abbuchungen (das läuft nach dem Einschalten nach).
  5. Wenn möglich eine Testabbuchung (kleiner Betrag, Testkonto) und Erstattung.
  6. Einschalten; danach der Alarm `card:switch-off` ist weg und die Anzeige steht auf EIN.
  7. Betroffene informieren (Turnierveranstalter, Teams mit eingefrorenen Turnieren, Support).
  Betroffene (Spieler, Turnierveranstalter) werden nicht automatisch informiert (Backlog 210). Der Buchungsstab (Admin 1 und Admin 2, nicht gesperrt, der Akteur selbst ausgenommen) bekommt bei jedem Umschalten eine Mitteilung "Kartenzahlung ausgeschaltet" bzw. "eingeschaltet" (Typ `system.critical`: nicht abschaltbar, nur In-App, ohne Grund und ohne Namen; Link `/admin/finanzen`) zusätzlich zum Alarm. Steht in der Einstellung etwas anderes als `true`/`false`, meldet die Oberfläche "unerwarteten Wert … per SQL prüfen" und ändert nichts (dann den Wert mit dem Statement oben auf einen Boolean setzen).

- Restfenster: ein Netzaufruf, der Millisekunden vor dem Umlegen gestartet wurde, geht noch raus und wird normal verbucht.

### Lokale Entwicklung mit Stripe-Testmodus (Kurzfassung)

Die Einzelheiten stehen oben; hier die Reihenfolge für Worker-Worktrees. Nur Namen, nie Werte.

### Zahlungen AUS bei eingeschaltetem Kartenmodell (Gratis-/Testbetrieb)

**`payments_enabled` AUS = Gratis-/Testbetrieb. In Produktion nur bewusst ausschalten.** Wirkung bei `card_payments_enabled` EIN und `payments_enabled` AUS:

| Gegenstand | Verhalten |
|---|---|
| Neue Beitritte und Bereit-Meldungen in Spielen (Frist-Regel) | kostenlos, keine Karte verlangt (`cardModeActive` liefert false) |
| Captains bestätigen ein solches Spiel | der Anteil wird als 0 fixiert (kostenlos); keine Abbuchung, keine Provision, auch nicht nach dem Wiedereinschalten |
| Spiel mit begonnener Abrechnung (Abbuchungs- oder Erstattungszeilen, fixierter Anteil > 0, Platz `charge_pending`/`charged`) | bleibt unverändert im Kartenmodell: Abbuchung, Nachzahlfenster, Erstattung und Frist-Regel laufen weiter (`isChargeBound`); kein Geld verschwindet, keine Doppelbelastung |
| Spiel mit Karte, aber ohne Abrechnung | friert nicht ein (eine hinterlegte Karte allein bindet nicht) |
| Turnier mit Preis | wird NICHT kostenlos: bleibt eingefroren (wie bei Karte AUS): keine Abbuchung, keine Absage durch das Nachzahlfenster, Alarm für Admin 1 ab 6 Stunden (`tournamentPaymentsActive`) |
| Zusage der Halle (Turnier) | unabhängig von Zahlungen: die Erinnerung 24 h/6 h vor der Frist (`notifyHallConfirmReminders`) läuft auch bei AUS und bei eingefrorenen Turnieren; Zusage = Buchungsbedingung |
| Wiedereinschalten (`payments_enabled` EIN) | Spiele ohne Karte, nicht fixiert, kehren ins Kartenmodell zurück: Karten nachholen, sonst Absage zur Frist (nichts abgebucht, kein Geldverlust); kostenlos fixierte Spiele bleiben kostenlos |

Der Schalter wirkt nicht rückwirkend auf bezahlte Plätze.

**Ertragsverzicht:** Ein bei AUS bestätigtes Spiel ist mit Anteil 0 fixiert und bleibt auch nach dem Wiedereinschalten kostenlos (keine Abbuchung, keine Provision). Das ist gewollt und entgeht dem Ertrag; vor dem Ausschalten in Produktion bedenken (siehe GO-LIVE-AUDIT). Ein Spiel mit Guthaben im Spiel (`paid_cents > 0`) wird nie gratis fixiert. **Turniere:** Ein bei AUS angelegtes oder fixiertes Turnier mit Preis bekommt beim Fixieren Halle, Zugangs-Snapshot und Provisionssatz (Kartenfluss) und ist damit eingefroren (Alarm ab 6 Stunden, keine Abbuchung, keine Absage); es wird nie still kostenlos. Das Anlegen verlangt bei eingeschaltetem Kartenschalter weiterhin eine Partnerhalle.

## Admin 1 festlegen (Vertrag 009 M1, nur Betreiber)
Admin 1 (Seitenbetreiber) ist das eine Konto mit `users.role = 'admin'` UND `users.is_owner = true`; die Datenbank erlaubt höchstens eines. Es entsteht nie von selbst: Die Migration setzt niemanden, das macht dieser Schritt.

**Reihenfolge beim Einspielen:** 1. Migration (der übliche Update-Ablauf führt `scripts/migrate.mjs` aus) und Code E1a (Spalte, Skript; Verhalten unverändert, Admin 1 trägt weiter die Rolle `admin`) → 2. **Admin 1 festlegen** (dieser Abschnitt) → 3. erst danach Code E1b (Finanzen, Einstellungen und Rollenvergabe nur noch für Admin 1; Admin 2 verliert sie) → 4. danach Alarme nur an Admin 1 (E2). **E1b nie vor Schritt 2 ausrollen:** sonst hat bis zum Festlegen niemand Zugriff auf Finanzen und Einstellungen.

**Festlegen** (ein BESTEHENDES Konto mit `role = 'admin'`, das sich einmal angemeldet hat; Datenbank aus `DATABASE_URL`, Konto aus `OWNER_EMAIL`, beides aus der Umgebung des Servers, der Wert steht nie im Repo und wird nie ausgegeben; Name der Angabe in `docs/loop/FEHLT-NOCH.md`):
```
OWNER_EMAIL=<email> node scripts/set-owner.mjs          # Trockenlauf: zeigt nur Host, Port und Datenbankname
OWNER_EMAIL=<email> node scripts/set-owner.mjs --yes    # führt aus
```
Ohne `OWNER_EMAIL` handelt das Skript nur, wenn es genau EIN nicht gesperrtes Admin-Konto gibt; bei mehreren bricht es ab (keine Raterei). Ein E-Mail-Argument auf der Kommandozeile wird abgelehnt.
Das Skript ist idempotent (zweiter Aufruf für dasselbe Konto: „Unverändert“), bricht ab, wenn ein ANDERES Konto schon Admin 1 ist, das Konto fehlt, kein Admin-Konto oder gesperrt ist, und schreibt einen Protokolleintrag `user.owner_set` ohne Akteur. Es zeigt nie E-Mail, Benutzer oder Passwort.

**Release-Bedingung (Security-Review E1c):** E1c (Teilrollen-Migration und -Code) und E2 (Alarme nur an Admin 1, `ownerIds`) gehen im SELBEN Release produktiv. Bis E2 gehen die täglichen Finanz-Alarme an alle nicht gesperrten Admin-Konten, auch an Admin 2; dessen Link `/admin/finanzen` leitet auf `/app` um (keine Finanzrechte). E1c allein ausrollen ist daher nicht zulässig.

**Teilrollen (Entscheid t9):** Die Migration `…_teilrollen_aufloesen` setzt Konten mit `moderator`, `finance` und `booking` automatisch auf `player` (geringste Rechte) und schreibt je Konto einen Protokolleintrag `user.role` (Akteur leer, `before.role` = frühere Rolle, Grund in `after.reason`). Die Enum-Werte bleiben bestehen. **Rollback:** nicht automatisch; die Rolle jedes Kontos steht im Protokoll (`select entity_id, before from audit_log where action = 'user.role' and after->>'reason' like 'Rolle aufgelöst%'`) und lässt sich daraus von Hand zurücksetzen. Danach ernennt ein Admin-Konto Admin 1 bewusst (dieser Abschnitt).

**Ein anderes Konto soll Admin 1 werden (Übergabe):** zuerst das alte Konto freigeben (`update users set is_owner = false where email = '<alt>'`), dann das Skript für das neue Konto. Ohne Admin 1 gehen die Alarme ab E2 nicht an Dritte (nur Server-Log), deshalb die Lücke kurz halten.

**Rückgängig (Rollback):** Code auf den vorherigen Stand zurück; Admin 1 lässt sich ohne Datenverlust abgeben (`is_owner = false`). Die Spalte `is_owner` und der Teilindex `users_one_owner` bleiben ungenutzt stehen (Datenbankänderungen sind nur vorwärts, vorher sichern).

**Prüfung der Migration** (lokal, Wegwerf-Datenbanken, löscht sie danach): `node --env-file=.env.local scripts/migrate-check.mjs` (frische Datenbank mit allen Migrationen in einem Lauf und bestehende Datenbank mit Daten).

## Hallen-Anfragen freischalten (013 v3, AC-31, Migration 0056)

- Eine Halle aus der Anfrage ("Anfrage senden", Hallen-Onboarding M2d) wird im Status `requested` angelegt (inaktiv, keine Partnerhalle, Standard-Provision) und bekommt für den Anfragenden einen aktiven Betreiber-Zugang. **Sichtbar und buchbar ist sie erst nach der Freischaltung** durch Admin 1 oder Admin 2 unter `/admin/hallen/anfragen` (Freischalten, oder Ablehnen mit Grund, 3 bis 200 Zeichen). Der Betreiber bekommt eine Mitteilung; unter `/halle` sieht er den Status. Nach einer Ablehnung kann er die Anfrage nach einer Änderung erneut senden (keine Sperrfrist), die Historie bleibt im Eingriffsprotokoll (`venue.requested/approved/rejected`, IDs und Grund, keine Personendaten).
- **Anfrage-Server (M2d-1, Migration 0057):** `requestVenueAction`/`resubmitVenueAction` (`src/server/venue-request-actions.ts`) prüfen die Sitzung und dann ausschließlich die gemeinsame Quelle der Oberfläche (`src/lib/venue-onboarding.ts`: `werteAusFormData`, `parseOnboarding`). `requestVenue` legt in EINER Transaktion Halle (`requested`, inaktiv, `court_count` 1 bis 50), Betreiber-Zugang, zwei Preisregeln (60 und 90 Minuten, Preis = Kosten, ab heute (UTC-Tag, wie `addPriceRule`); Admin 1 stellt die Kosten später) und den Audit-Eintrag (Plätze, Bedingungstext-Schlüssel und -Version, KEIN Kontakt, keine Adresse) an; eine Wiederanfrage ERSETZT die Preisregeln. **Grenzen je Nutzer:** höchstens 5 Anfragen (auch Wiederanfragen) pro Stunde (gezählt aus `audit_log`, atomar unter dem Sperrschlüssel je Nutzer) und höchstens 3 offene Anfragen; Admin- und gesperrte Konten sind ausgeschlossen. Der Audit-Eintrag enthält zusätzlich die Preise je Termin in Cent (kein Personenbezug; Spur für einen Streit um die Miete). Eine **Wiederanfrage ersetzt still** alle Preisregeln der abgelehnten Halle, auch von Admin 1 angelegte (bewusst akzeptiert). Preise: beide (60 und 90 Minuten) oder keiner; `valid_from` ist der UTC-Tag wie bei `addPriceRule`/`priceFor`. Eine zweite Anfrage mit gleichem Namen und gleicher Stadt und ABWEICHENDEN Angaben wird mit "Diese Anfrage liegt schon vor" abgewiesen (kein stilles Verschlucken), mit identischen Angaben ist sie ein ok (Doppelklick). Der Bedingungstext ist ein ENTWURF bis zur Anwaltsprüfung (Rechtsliste). **Rollback Migration 0057:** `drizzle/down/0057_down.sql`.
- Der Server prüft überall: jeder Leser (Hallenliste, Detail, Sitemap, Termin-Auswahl, Hallen-Veto, Turnier-Partnerhalle) filtert auf `approval_status = approved` zusätzlich zu `active`; beim Zuordnen einer Halle (Buchungsauftrag, Turnier) antwortet eine nicht freigegebene Halle wie eine unbekannte ID (kein Existenz-Leck). `updateVenue` aktiviert eine angefragte oder abgelehnte Halle nie.
- **Entwickler-Datenbanken mit einem früheren Stand von 0056:** Die Migration 0056 wurde vor dem Merge überarbeitet (erst ohne, dann mit dem CHECK `venues_requested_inactive_chk`). Eine Worker-Datenbank, die einen früheren Stand schon angewendet hat (z. B. `soccaz_w1` bis `soccaz_w4`), muss VOR dem Update `drizzle/down/0056_down.sql` ausführen UND den Eintrag `0056_venue_approval` aus `drizzle.__drizzle_migrations` löschen (der neueste Eintrag), oder die Datenbank neu anlegen (`node scripts/worktree.mjs remove`/`create`). Sonst scheitert `npm run db:migrate` (Spalten existieren schon) oder der CHECK fehlt. Produktion ist nicht betroffen (die Migration wurde dort nie angewendet).
- Bestehende Hallen (Altbestand, OpenStreetMap-Import, Admin-Anlage) sind `approved` und unverändert sichtbar (Standardwert der Migration, kein Backfill nötig). **Rollback:** erst den Code zurückrollen, dann `drizzle/down/0056_down.sql` im Wartungsfenster (rein additiv).

## Hallenbetreiber: Zugang je Halle (Vertrag 011 M1, nur Admin 1)

- **Einladen:** Admin 1 gibt in `/admin/hallen` die Google-E-Mail des Betreibers für eine Halle frei (Grund wird protokolliert, nur IDs, nie die Adresse). Es wird **keine Mail verschickt**: Der Betreiber meldet sich selbst mit genau dieser Google-Adresse an. Je Halle gibt es höchstens einen Zugang (geteilt mit den Mitarbeitern); eine neue Einladung ersetzt und entzieht den bisherigen Zugang sofort.
- **Aktiv wird der Zugang beim nächsten Login mit Google und verifizierter E-Mail** (nie über den Dev-Login). Auch bestehende Konten laufen über diesen Weg. Eine Einladung gilt **14 Tage**; danach lädt Admin 1 neu ein oder zieht sie zurück. Mehrere Hallen derselben Firma: je Halle eine Einladung mit derselben Adresse, ein Login löst alle offenen ein.
- **Entzug** (auch einer noch offenen Einladung) wirkt sofort und ohne neue Anmeldung; gesperrte Konten und Admin-Konten haben nie Zugang (Admin ist nicht Betreiber). **Offene Anfragen** einer Halle ohne Zugang werden „unmanaged“ (nicht abgelehnt), die Auswertung läuft weiter. Beim Löschen des Betreiber-Kontos wird der Zugang entzogen und die Adresse geleert.
- **Datenübernahme:** Die Migration `0049_venue_access` legt für jede Halle mit bisherigem Betreiber (`venues.manager_user_id`) einen aktiven Zugang an, außer bei verwaisten (kein Konto), anonymisierten und Admin-Konten. Diese Hallen gelten danach als **ohne Zugang**: Admin 1 lädt vor dem Rollout neu ein. Liste vorher prüfen: `select id, name from venues v where manager_user_id is not null and not exists (select 1 from venue_access a where a.venue_id = v.id)`. Gesperrte Konten werden übernommen, haben aber keinen Zugriff (wieder aktiv nach Entsperren).
- **Aufbewahrung der Adresse (t9 R1):** Rückzug, Entzug und Konto-Löschung leeren die Adresse sofort. Eine nie eingelöste Einladung bleibt `invited` und wird vom Job `expire-venue-invites` (täglich 03:23 UTC) **44 Tage nach dem Einladen** (14 Tage gültig + 30 Tage) auf `revoked` gesetzt und die Adresse geleert (Eingriffsprotokoll `venue.access.expire`, ohne Adresse).
- **Migrationsbericht (nur lesend):** `node --env-file=.env.local scripts/venue-access-report.mjs` zeigt vor dem Rollout (Vorhersage) und danach die Hallen ohne aktiven Zugang mit Grund und offenen Anfragen, nie E-Mail-Adressen.
- **Rückfall:** `venues.manager_user_id` wird in jedem Pfad mitgeschrieben und bleibt bis 011 M4 bestehen; gelesen wird `venue_access` (hasVenueAccess).

## Wartungsausnahme der Datenbank-Trigger und DB-Rollenmodell (bekannte Grenze, Entscheid t9)
Das Hauptbuch (`ledger_entries`), `match_commissions`, `invoices`, `invoice_lines`, das Beweisprotokoll (`booking_evidence`, `booking_evidence_counter`) und `matches.ledger_model` sind per Datenbank-Trigger gegen UPDATE, DELETE (und beim Beweisprotokoll TRUNCATE) gesperrt. Eine **Wartungsausnahme** erlaubt die Änderung nur innerhalb EINER Transaktion mit `set local socaz.ledger_maintenance = 'on'` (bzw. `select set_config('socaz.ledger_maintenance', 'on', true)`).
**Bekannte Grenze:** Dieser Wert ist ein **freier Sitzungswert**. Jede SQL-Anweisung, die die App-Datenbankrolle ausführen kann, kann ihn selbst setzen; die Trigger schützen also gegen Fehler und gegen versehentliche Änderungen, **nicht gegen eine Rolle, die bösartig oder kompromittiert ist**. Dasselbe gilt für die Sitzungsvariable `socaz.evidence_insert` (Zählerschutz des Beweisprotokolls, nur während des INSERT-Triggers gesetzt). Es gibt (noch) **keine getrennten Datenbankrollen**.
**Was der App-Code tut:** Der Wartungswert wird in `src/` und `scripts/` nirgends gesetzt; ein Test (`tests/unit/maintenance-guard.test.ts`) prüft das im Quelltext (Allowlist: `tests/`, `drizzle/`, ausdrücklich benannte Wartungsskripte, derzeit keine). Wer ein Wartungsskript braucht, trägt es mit Begründung in die Allowlist ein.
**Restrisiko Kettenumschreibung (Entscheid t2q): bis der tägliche Anker (separater Speicher, `docs/design/g25-009-db-rollenmodell.md` Abschnitt 11) umgesetzt ist, ist die ungeschlüsselte Hash-Kette nur durch Vergleich des täglichen Kopf-Hashs (Benachrichtigung an Admin 1) mit der externen Kopie von Hand prüfbar; HMAC ist Folgeentscheid nach dem Pilot.**
**Entscheid t2q (G25-009): zweite Verbindungsrolle `soccaz_ops` (nur `evidence_set_setting`, `evidence_late_attempt`) ist Pflicht vor Go-live, eigene Etappe nach #155 und 011 M2a/b; Plan: `docs/design/g25-009-db-rollenmodell.md`. Bis dahin Restrisiko: beide Funktionen sind für die App-Rolle ausführbar und ändern Einstellungen/Einträge nur über diese Funktionen, mit Audit.**
**Pflicht vor Go-live (GO-LIVE-AUDIT G25-009, blockiert Go-live):** getrennte Datenbankrollen: eine **App-Rolle** ohne Recht, den Wartungswert zu setzen oder die Trigger zu umgehen (kein Schema-Recht, kein `ALTER TABLE`, kein `DISABLE TRIGGER`, kein `SET` der `socaz.*`-Werte, z. B. über `ALTER ROLE … SET` und entzogenes Recht), und eine davon **getrennte Migrations-/Wartungsrolle**; dazu `REVOKE` aller nicht benötigten Rechte und das **Hosting-Rollenmodell** des Anbieters. Vorschlag zur Härtung (noch nicht gebaut): die Trigger prüfen zusätzlich `current_user` (nur die Wartungsrolle darf die Ausnahme nutzen) statt eines frei setzbaren Wertes. Prüfung vor Live: als App-Rolle `set_config('socaz.ledger_maintenance','on',true)` und ein `UPDATE` auf das Hauptbuch müssen scheitern.

Zieht ein Guthabenzahler seine Zahlung zurück (Rückzug aus dem Spiel), entfällt die Provision für dieses Spiel dauerhaft. ## Beweisprotokoll: Löschen von Hallen und Sperrreihenfolge (009 M3)
- **Hallen löschen:** Es gibt keinen Schutz gegen das Löschen einer Halle, zu der Beweisprotokoll-Einträge existieren (nur Spiele sind geschützt: Trigger auf `matches`). Die App löscht nie Hallen (nur aktiv/inaktiv). Wird eine Halle manuell gelöscht, meldet der Tagesjob `evidence-head` die verwaisten Einträge als **Alarm** an Admin 1 (die Kette bleibt gültig). Hallen daher nicht löschen, sondern deaktivieren.

- **Beweisprotokoll-Einträge entstehen per Datenbank-Trigger beim COMMIT** (nicht in der Anwendung); Wartungsausnahme und Rollenmodell: Abschnitt „Wartungsausnahme der Datenbank-Trigger“.

- **Durchsetzungs-Schalter `evidence_enforcement`:** nach der Migration `off` (Bestandsverhalten: Einträge entstehen, Pflichtbegründung und Frist-Fehler gelten nicht). **Go-live nur mit `on`.** Einschalten ist eine **Admin-1-Aktion** über die SQL-Funktion `evidence_set_setting` (Akteur Pflicht, Eintrag im `audit_log`, umkehrbar) und erst möglich, wenn `evidence_clock_source = 'db'` (011 M2a: DB-Zeit, strikt `>`). Ein fehlender oder ungültiger Schalter gilt als `on` (fail-closed). Der Tagesjob `evidence-head` meldet an jedem Lauf, solange der Schalter `off` steht.
- **Geschützte Einstellungen** (nur über `evidence_set_setting`, nie über `setSetting`): `evidence_enforcement`, `evidence_clock_source`, `evidence_reason_retention_days`, `evidence_cutover_at`, `evidence_tournament_cutover_at` (die Stichtage blenden Zeilen aus dem Abgleich aus, der Aufbewahrungswert hat noch keinen Job, siehe unten). Grenze wie bei der Wartungsausnahme: kein Schutz gegen jeden mit SQL-Zugriff (G25-009).
- **Ausrollen:** `ALTER TABLE match_hall_requests` nimmt kurz `ACCESS EXCLUSIVE` (kleine Tabelle): in einem ruhigen Fenster ausrollen. Reihenfolge: Nachlieferung (Schalter aus), dann 011 M2a (Sitzungswerte Code/Grund, DB-Zeit), dann Admin 1 schaltet ein.
- **Begründungstext:** Klartext liegt nur in `booking_evidence_reason_text` (im Hash nur das Commitment); Löschen **nur per DELETE** (ein UPDATE bricht das Commitment). `deleteAccount` und der Job `evidence-head` löschen ihn; Backups, WAL und Logs erreicht das Löschen nicht (Frage R3). Der Export enthält nie Klartext (Ausnahme: Altzeilen Version 1, deren Klartext im Hash steht, Ansicht `evidence_legacy_plaintext`).
- **Prüfung:** `verifyEvidenceChain` meldet `hash`, `prev_hash`, `seq-luecke`, `zaehler` und `commitment`; fehlender Klartext gilt als nicht prüfbar. Zu früh abgelaufene Einträge (`expired` mit Zeit vor dem Fristende) meldet der Abgleich (`early_expiry`).
- **Bei Abbruch des Mutationsskripts** (`scripts/mutation-evidence.mjs`): die Worker-Datenbank neu anlegen UND die Quelldateien prüfen (`git status`, `git diff src`; Mutationen mit `file` schreiben `src/server/account.ts` und `src/server/evidence.ts` um): mit `git checkout -- <Datei>` zurücksetzen.
- **Aufbewahrung des Klartexts:** der Tagesjob `evidence-head` löscht Begründungs-Klartext (nur `booking_evidence_reason_text`), dessen Eintrag älter ist als `evidence_reason_retention_days` Tage; **Standard `0` = aus** (gültig 1 bis 36500; ungültige Werte, auch 36501 bis 99999, löschen nichts und werden in der Tagesbenachrichtigung gemeldet; Anker = Eintragszeit `booking_evidence.at`, Stichtag = Datenbankuhr; höchstens 10 000 Texte je Lauf; ein Lauf mit ungültiger Kette löscht nichts: bei dauerhaft ungültiger Kette bleibt die Aufbewahrung ausgesetzt, bis der Befund geklärt ist; die Löschung von Klartext zu anonymisierten Konten (Kontolöschung) läuft dagegen immer, vor der Kettenprüfung, und ist gewollt), Anzahl im `audit_log` (`evidence.retention`). Die **Dauer legt der Anwalt fest (R3, Freigabebedingung für Go-live, GO-LIVE-AUDIT G26-009)**; gesetzt wird sie von Admin 1 über `evidence_set_setting`. Backups, WAL und Logs erreicht das Löschen nicht.
- **Kettenprüfung bei wachsender Kette:** 100 000 Zeilen ca. 2,2 bis 2,9 s (Messung, Backlog 165); ab etwa 100 000 Zeilen inkrementelle Prüfung einplanen (Backlog 166).

## Sperrreihenfolge (Backlog 144, 012-Rest PR C)
Jede Transaktion, die mehrere Zeilen sperrt, hält sich an EINE Reihenfolge: **Halle (sortiert) → Zugang → Turnier (sortiert) → Spiel (sortiert) → Zahlungszeile → Nutzer**; nie rückwärts, und wer ein Turnier hält, **wartet nie auf ein Spiel**.
- **Absage** (`cancelTournamentTx`): Turnier, **sofort danach** die Spiele des Turniers sortiert mit `NOWAIT` (Wiederholung 50/100/200 ms, danach „Bitte gleich noch einmal versuchen“), erst dann Erstattungs- und Zahlungszeilen. Das Protokoll `tournament.cancel_busy` (ohne Personendaten) schreibt der Aufrufer **nach dem Rollback**; der Job versucht es im nächsten Lauf, nie stilles Auslassen.
- **Kontolöschung** (`deleteAccount`): Turniere (auch die der betroffenen Spiele); **dann die Löschsperre** (wer in einem laufenden Turnier steht, wird abgelehnt, ohne ein Spiel zu sperren); die Spiele, die zu einem Turnier gehören, mit `NOWAIT`; danach die Teamspiele blockierend (sortiert), Zeilen, Nutzer.
- **Ergebnis-Finalizer** (`advanceFromMatch`): das Spiel hält der Aufrufer, dann das Turnier: die einzige erlaubte Rückrichtung, weil Absage und Löschung unter der Turniersperre nie auf ein Spiel warten.
- **Abbuchung/Zusage/Fixieren/Erinnerungen (Turnier):** nur das Turnier (dann Zahlungszeile); der Zugang wird gelesen, nie gesperrt. **Zugang einlösen** (`redeemVenueInvites`): Hallen → Zugangszeilen → Turniere (gilt nur dort, nicht für die Löschung). **Bekannte enge Ausnahme:** die Kontolöschung hält ein Turnier und ruft später `revokeAccessOfUser` (sperrt die Halle blockierend): Turnier → Halle, gegenläufig zu `redeemVenueInvites`/`armConfirmationForNewAccess`; Zyklus schon vor PR C, schlimmstenfalls ein Transaktionsabbruch (40P01), `redeem` fängt ihn im Savepoint; kein Datenfehler. **Teamspiel-Abbuchung:** Spiel → Zeile → Nutzer.
**Neue Pfade** halten die Reihenfolge ein oder warten nie (`NOWAIT`); Strukturtest `tests/unit/lock-order.test.ts`, Verhalten `tests/integration/tournament-lock-order.test.ts` (rohe zweite Verbindung als Barriere).

## Wartungsausnahme an die Rolle gebunden und Restore-Modus (G25-009 A1, Migration 0055)
- `socaz_maintenance_allowed()` ersetzt in allen Triggern/Guards die Rohprüfung des Sitzungswerts `socaz.ledger_maintenance`: die Ausnahme gilt nur, wenn der Wert gesetzt ist **und** `session_user` Mitglied von `soccaz_maintenance` ist (Superuser sind implizit Mitglied). **Zwischenzustand:** existiert die Rolle `soccaz_maintenance` in der Datenbank nicht (Datenbank ohne Rollen), gilt wie bisher nur der Wert; mit A2 wird das hart. **A1 allein schließt G25-009 nicht** (GO-LIVE-AUDIT: erst nach A2).
- **Logischer Restore der Beweiskette** (nur im Ausnahmefall; Regelfall ist die physische Wiederherstellung/PITR): als Mitglied von `soccaz_maintenance` in EINER Transaktion `select set_config('socaz.ledger_maintenance','on',true); select evidence_restore_begin();` (verlangt eine **leere** Zieltabelle `booking_evidence` mit Zähler 0), dann die Zeilen mit unveränderten `seq`/`prev_hash`/`at`/`hash` einfügen (jede Zeile wird geprüft: lückenlose `seq`, `prev_hash` = Hash der Vorzeile, Hash stimmt, `at` nicht rückwärts), am Ende `select evidence_restore_finish('<erwarteter Kopf-Hash aus der externen Kopie/dem Anker>')` (Pflicht; Kopf-Hash und Zeilenzahl müssen zum Zähler passen), `commit`. Danach `verifyEvidenceChain` und Vergleich mit der Benachrichtigung/dem Anker. Ohne diesen Modus ist ein logischer Restore der Beweistabellen verboten. Wartungs-/Restore-Verbindungen nie über einen Transaktions-Pooler (`set_config(…, true)` nur in einer Transaktion auf direkter Verbindung).
- Rückfall nur VOR A2: `drizzle/down/0055_down.sql` (kein Sicherheits-Rückfall, stellt die Rohprüfung wieder her; danach den Journal-Eintrag von Hand entfernen).
- **Rolle existiert = harte Prüfung (clusterweit):** ob `soccaz_maintenance` existiert, entscheidet `pg_roles`, und Rollen gelten für den **ganzen Cluster**. Sobald `db-roles.mjs --apply` die Rollen angelegt hat, wechseln **alle** Datenbanken dieses Clusters (auch `soccav2` und `soccaz_w1` bis `w4`) beim nächsten Migrieren auf die Mitgliedschaftsprüfung: die Wartungsausnahme gilt dann auch lokal nur für Mitglieder (Superuser sind implizit Mitglied; `postgres`-Tests und `tests/cleanup.ts` bleiben unverändert).
- **Restore, Hinweise:** im Restore-Block **kein Savepoint und kein `ON_ERROR_ROLLBACK`** (die Fortsetzung prüft, ob die Vorzeile in derselben Transaktion eingefügt wurde; eine Unter-Transaktion lehnt sie fail-safe ab). Der erwartete Kopf-Hash für `evidence_restore_finish` stammt **nur aus der externen Quelle** (Benachrichtigung an Admin 1, später Anker), nie aus der wiederherzustellenden Datenbank selbst. `at` wird auf NULL und auf mehr als eine Minute in der Zukunft geprüft, die Monotonie je Zeile. Dass ein Wartungsmitglied eine Kette mit passendem Kopf-Hash neu berechnen könnte, ist plankonform offen (HMAC-Entscheid nach dem Pilot, Anker Abschnitt 11 des Plans).

## DB-Rollen: Skripte (G25-009, Etappe D; noch ohne Wirkung auf die Anwendung)
- `node scripts/db-roles.mjs [--apply]` legt die Rollen `soccaz_owner`, `soccaz_maintenance`, `soccaz_migrate`, `soccaz_app`, `soccaz_ops`, `soccaz_backup` an (idempotent; ohne `--apply` nur Trockenlauf). **Passwörter nur aus Umgebungsvariablen** (`DB_PASSWORD_MIGRATE`, `_APP`, `_OPS`, `_BACKUP`), nie im Repository, nie in der Ausgabe. Nur gegen lokale Datenbanken (Wächter wie `db-guard`); ein Lauf gegen einen fremden Host braucht Freigabe des Task Managers und gehört nicht in dieses Skript.
- `node scripts/db-owner.mjs --plan <datei>` (Trockenlauf) schreibt je Objekt die Anweisung `ALTER … OWNER TO soccaz_owner` samt bisherigem Eigentümer und gibt die **SHA-256** aus. Anwenden nur mit `--apply --plan <datei> --plan-sha256 <Summe>` (Summe getrennt übergeben, Zieldatenbank der Datei muss zur Verbindung passen, neue Objekte seit dem Plan = Abbruch); Rückfall mit `--reverse`. **Kein `REASSIGN OWNED`**, der Datenbankbesitzer wird nie angefasst. Anwenden erst mit Etappe A2.
- Die CI legt die Rollen an und prüft den Eigentumswechsel im Trockenlauf (Job "Integrationstests").
- Passwörter setzt `db-roles.mjs` nur als **SCRAM-SHA-256-Verifier** (clientseitig gebildet, der Klartext steht nie in einer Anweisung, im Serverlog oder in `pg_stat_statements`). Rollen ohne gesetztes Passwort (Variable fehlt) dürfen in `pg_hba.conf` **nicht** über `trust` erreichbar sein. `soccaz_backup` liest über `pg_read_all_data` clusterweit in jeder Datenbank, in der `CONNECT` offen ist.
- `db-roles.mjs` gleicht die **Mitgliedschaften** gegen die Soll-Liste ab (nur `soccaz_migrate` → `soccaz_owner`, `soccaz_backup` → `pg_read_all_data`), entzieht Abweichungen zwischen unseren Rollen und **bricht bei fremden Mitgliedern ab**; rollenbezogene Einstellungen (`ALTER ROLE … SET`) werden entfernt. Läufe sind per Advisory-Lock serialisiert (Rollen sind clusterweit).
- **Bekannte Lücken von `db-owner.mjs`** (nicht erfasst, Meldung durch die Katalog-Positivprüfung in A2): Operatoren, Operatorklassen/-familien, Kollationen, Textsuche-Objekte, Konversionen, erweiterte Statistiken, Ereignis-Trigger, Publikationen. Beim Anwenden werden die Anweisungen aus den Strukturfeldern neu gebaut und mit der Datei verglichen (manipulierte Datei = Abbruch vor jeder Ausführung), `lock_timeout` 5 s, Prüfung auf neue Objekte und Nachprüfung innerhalb der Transaktion.
- **Sperrliste:** `--apply` (db-roles und db-owner, auch `--reverse`) wird gegen `soccav2` und jede nicht freigegebene Datenbank **verweigert**; Standard-Erlaubnis nur `soccaz_w1` bis `soccaz_w4`, die Wegwerf-Namen der Skripte und im CI `socaz`. Alles andere nur mit `--allow-database <exakter Name>` (Freigabe des Task Managers). `--database <name>` muss die Datenbank der Verbindung sein. Der Trockenlauf bleibt immer erlaubt.
- **Einmaliger Katalog-/pg_hba-Check vor der Umsetzung (Superuser, lesend):** `select line_number, type, database, user_name, address, auth_method from pg_hba_file_rules where auth_method = 'trust';` darf für den Cluster 5433 keine Zeile liefern, die die `soccaz_*`-Rollen erfasst (lokal ist `trust` für `127.0.0.1` häufig: dann den Zugriff dieser Rollen per eigener `scram-sha-256`-Zeile davor erzwingen). Das Ergebnis wird im GO-LIVE-AUDIT (G25-009) festgehalten.
- **Passwörter** nur druckbares ASCII ohne Leerzeichen (SASLprep wird nicht nachgebaut; anderes wird abgelehnt); eine leere `DB_PASSWORD_*` ist ein Fehler, eine nicht gesetzte Variable lässt die Rolle ohne Passwort (siehe pg_hba).
- **Mitgliedschaften:** die erlaubten Mitgliedschaften dürfen kein `ADMIN OPTION` tragen und müssen `INHERIT` und `SET` haben (PostgreSQL 16+); `db-roles.mjs` korrigiert das und bricht sonst ab.
