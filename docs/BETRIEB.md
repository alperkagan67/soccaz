# Betrieb

Alles läuft mit Docker Compose: App, PostgreSQL, Caddy (HTTPS) und eine tägliche Sicherung. Kein Kubernetes.

## Erstinstallation (Server, z. B. Hetzner Cloud CX22)

1. Server mit Ubuntu 24.04, Docker und Docker Compose installieren, Domain per A-Record auf die Server-IP legen.
2. Repository klonen: `git clone https://github.com/alperkagan67/soccaz.git && cd soccaz`
3. Konfiguration anlegen: `cp .env.production.example .env` und alle Werte eintragen (Datenbankpasswort, Domain, `AUTH_SECRET`, Google, `JOB_SECRET`).
4. Starten: `docker compose up -d --build`
5. Prüfen: `https://deine-domain/api/health` liefert `{"status":"ok"}`.
6. Den ersten Admin festlegen (einmalig, nach der ersten Anmeldung):
   `docker compose exec db psql -U socaz -c "update users set role='admin' where email='deine@mail.de'"`

Die Migrationen laufen automatisch bei jedem Start (`migrate`-Dienst).

## Hallenliste

Die Datei `data/nrw-hallen-osm.json` enthält Soccer- und Fußballhallen in NRW aus OpenStreetMap (ODbL, ungeprüft). Einspielen (mehrfach ausführbar, überschreibt keine geprüften Hallen):

```
docker compose run --rm migrate node scripts/import-venues.mjs
```

Neu abrufen: `node scripts/fetch-venues-osm.mjs` (braucht Internet, dauert eine Minute). Im Admin-Bereich unter Hallen markierst du eine Halle als geprüft, sobald Buchbarkeit, Adresse und Preis stimmen. Geprüfte und Partnerhallen kommen im Veto zuerst.

## Überwachung

- **Fehler:** Sentry (`SENTRY_DSN` in der `.env`).
- **Erreichbarkeit:** Uptime Kuma als optionaler Dienst: `docker compose --profile monitoring up -d`. Er lauscht nur auf dem Server (Port 3001) und ist per SSH-Tunnel erreichbar: `ssh -L 3001:127.0.0.1:3001 <server>`. Beim ersten Öffnen Konto anlegen, dann einen HTTP-Monitor auf `https://<domain>/api/health` (Antwort `{"status":"ok"}`) und Benachrichtigung per E-Mail oder Telegram einrichten.
- **Geschäftszahlen** (Spiele, Umsatz, Guthaben, Auszahlungen) stehen im Admin-Bereich unter Finanzen. Prometheus und Grafana sind bewusst nicht dabei: Sie lohnen sich erst, wenn mehrere Server laufen.

## Betreiberangaben

Impressum und Datenschutzerklärung zeigen `OPERATOR_NAME`, `OPERATOR_ADDRESS` und `OPERATOR_EMAIL` aus der `.env`. Ohne diese Werte steht dort ein deutlicher Hinweis. Die Rechtstexte sind Entwürfe und müssen vor dem Start geprüft werden.

## Turniere und Veranstalter

Turniere dürfen nur freigeschaltete Veranstalter anlegen (Admin, Nutzer, „Als Turnier-Veranstalter freischalten“). Startgelder liegen bis zum Turnierende auf dem Konto `tournament`. Die Provision (Standard 10 Prozent) steht in der Tabelle `settings` unter `tournament_commission_percent`.

## Monatsjob

Am 1. jedes Monats schreibt `close-city-challenge` den Vormonat der Stadt-Challenge fest. Er ist mehrfach ausführbar und wirkt nur einmal. Alle Jobs: `src/server/jobs.ts`.

## Google-Anmeldung einrichten

Google Cloud Console, Projekt anlegen, APIs und Dienste, Anmeldedaten, OAuth-Client-ID (Webanwendung).
Autorisierte Weiterleitungs-URI: `https://deine-domain/api/auth/callback/google`. Client-ID und Geheimnis in `.env`.

## Update

```
git pull
docker compose up -d --build
```

Rückgängig: `git checkout <vorheriger-commit>` und erneut `docker compose up -d --build`. Datenbankänderungen sind nur vorwärts, deshalb vorher sichern.

## Sicherung und Wiederherstellung

- Täglich 03:30 UTC erzeugt der Dienst `backup` eine Sicherung in `./backups` (14 Tage Aufbewahrung).
- Sofort sichern: `docker compose exec backup sh /backup-loop.sh once`
- **Monatlich testen:** `sh scripts/restore-test.sh` stellt die neueste Sicherung in einer Wegwerf-Datenbank wieder her und zählt Tabellen und Nutzer. Eine Sicherung ohne diesen Test gilt nicht als Sicherung.
- Sicherungen zusätzlich außerhalb des Servers ablegen (z. B. Hetzner Storage Box per `rsync` oder `rclone`).
- Wiederherstellen in die echte Datenbank: `gunzip -c backups/socaz-….sql.gz | docker compose exec -T db psql -U socaz -d socaz`

Im Betrieb startet die App den Zeitplaner (pg-boss) selbst: Benachrichtigungen, Erinnerungen, automatische Absage, automatische Ergebnisbestätigung, Aufräumen. Einen Job von Hand anstoßen:

## Zahlungen einschalten

1. Rechtliches klären (Gewerbe, Steuer, AGB, Widerruf, Guthaben-Regeln). Siehe PLAN.md. Erst danach echtes Geld annehmen.
2. Stripe-Konto anlegen, Zahlungsmethoden (Karte, PayPal, SEPA) aktivieren.
3. In `.env`: `STRIPE_SECRET_KEY` und `STRIPE_WEBHOOK_SECRET` eintragen, Webhook-Endpunkt `https://deine-domain/api/webhooks/stripe` mit den Ereignissen aus `.env.production.example` anlegen.
4. `docker compose up -d --build`, dann im Admin-Bereich unter **Einstellungen** den Zahlungsanbieter prüfen (muss "Stripe" zeigen) und **Zahlungen einschalten**.
5. Testen mit Stripe-Testschlüsseln (`sk_test_...`, Testkarte 4242 4242 4242 4242), bevor die Live-Schlüssel eingetragen werden.
6. Preise stehen unter **Hallen** (Standardpreise: 60 Minuten 80 Euro, 90 Minuten 110 Euro). Hallenkosten und Marge sind dort pro Regel einstellbar.

### Kartenzahlung (Vertrag 012, Stripe)

- Eigener Webhook-Endpunkt `https://deine-domain/api/stripe/webhook` im Stripe-Dashboard, **getrennt** vom alten `/api/webhooks/stripe`. Stripe vergibt je Endpunkt ein eigenes Signaturgeheimnis (`whsec_...`): das der alten Route steht in `STRIPE_WEBHOOK_SECRET`, das der neuen in `STRIPE_CARD_WEBHOOK_SECRET`. Nie dasselbe Geheimnis für beide eintragen. Ereignisse der neuen Route: `setup_intent.succeeded`, `setup_intent.setup_failed` (Karte hinterlegen) sowie `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.requires_action` und `charge.updated` (Abbuchung, M2; beim Ausrollen von 012 M2a im Dashboard zusätzlich anmelden, sonst kommen keine Abbuchungsergebnisse an); später `charge.dispute.*`. Verspätete oder doppelte Ereignisse sind unkritisch (Idempotenz über `stripe_events`). Die alte Route `/api/webhooks/stripe` (Guthaben) entfällt mit 012 M6.
- Weitere Variablen: `STRIPE_SECRET_KEY` (gemeinsam) und `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`. **`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` wird beim BAUEN in den Browser-Code eingebettet** (Dockerfile `ARG`, `docker-compose.yml` `build.args`, Wert aus der `.env`); `env_file` allein reicht nicht. Nach jeder Änderung des Werts neu bauen: `docker compose up -d --build`. Ohne Wert zeigt die Lobby kein Kartenformular. `pk_` und `sk_` müssen aus demselben Modus stammen (Test: `pk_test_`/`sk_test_`; Live: `pk_live_`/`sk_live_`); Staging nie mit Live-Schlüsseln bauen.
- **Worktrees und Stripe-Testschlüssel:** Der Nutzer trägt `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` und `STRIPE_CARD_WEBHOOK_SECRET` in `.env.local` ein (Testschlüssel, nie Live). `worktree.mjs` kopiert `.env.local` nur beim ANLEGEN eines Worktrees: Bestehende Worktrees bekommen neue Schlüssel nicht automatisch (Worktree neu anlegen oder `.env.local` selbst abgleichen). Worker-Apps brauchen `stripe listen --forward-to localhost:<Port>/api/stripe/webhook` (Port des Workers 3101-3104) mit eigenem Webhook-Secret (`whsec_...`, aus der Ausgabe von `stripe listen`, nur in der eigenen `.env.local`). Agenten lesen und geben `.env*` nie aus.
- **Kartenmodell einschalten (Go-live-Schritt):** `card_payments_enabled` nur ohne offene bezahlte Spiele umlegen; bezahlte Spiele bleiben im Guthaben-Modell bis zum Ende. Technisch gilt das Kartenmodell nur für Spiele der Frist-Regel, in denen kein Platz `paid_cents > 0` hat; Erstattung bei Austritt, Neuberechnung und Fixieren laufen für Spiele mit bezahlten Plätzen unverändert über das Guthaben. Altspiele und Turniere bleiben beim Guthaben.
- **Abbuchung (M2):** Die Ereignisse stehen im ersten Punkt. Abgebucht wird je Spieler der fixierte Anteil, mindestens 0,50 EUR (Überschuss bleibt in revenue); kostenlose Spiele werden nicht abgebucht. **`card_payments_enabled` darf in Produktion erst nach M3 (Nachzahlfenster, Nachrücker, Erstattung) und M4 (Dispute, DSGVO, E2E im Testmodus) eingeschaltet werden, und zwar erst, wenn M3c-1 (Fenster und Wiederabbuchen), M3c-1c (3-D-Secure-Freigabe) UND M3c-2 (Nachrücker, automatische Absage) gemergt UND deployt sind:** bis dahin bleibt ein Spiel mit fehlgeschlagener Abbuchung unabgerechnet, es hängt nach dem Ende des Fensters, `requires_action` bleibt eine Sackgasse, und es gibt keine Rückerstattung (siehe GO-LIVE-AUDIT G8-012/G9-012).
- **Absage mit Erstattung (M3a):** Hat ein Spiel Abbuchungszeilen, sagt nur **Admin 1** ab (`adminCancelMatch` / `adminCancelMatchAction`; der Captain nur vor der ersten Abbuchung). Die Absage wird angefordert (`matches.cancel_requested_at`), ab dann wird nichts mehr abgebucht oder abgerechnet; jede erfolgreiche Abbuchung wird voll auf die Karte erstattet (Tabelle `payment_refunds`, eine Zeile je Abbuchung, fester Schlüssel `refund:<Zeile>`, Hauptbuch Soll `revenue`, Haben `clearing`; **die Stripe-Gebühr der Abbuchung bleibt bei Soccaz und wird nicht zurückgebucht**). Erst wenn alle Erstattungen erfolgreich und keine Abbuchung mehr offen ist, wird das Spiel `cancelled`. Gelingt eine Abbuchung erst nach der Anforderung, wird sie sofort erstattet. Abbuchungen mit unbekanntem Ausgang werden vor dem Abschluss per Stripe-Suche (Metadaten) gesucht; ein Treffer wird verbucht und erstattet, kein Treffer (nach 5 Minuten) bleibt Audit `charge.search_empty` + Alarm, das Spiel bleibt "Absage angefordert". Job `card-refunds` (alle 5 Minuten) bringt angeforderte Absagen weiter. Webhook-Ereignisse zusätzlich anmelden: `refund.created`, `refund.updated`, `refund.failed` (und `charge.refund.updated`, `charge.refunded` werden nur vermerkt). **Alarm für Admin 1** (`getRefundAlerts` in `finance.ts`): fehlgeschlagene Erstattungen (z. B. `charge_disputed`: manuell über Stripe klären), Erstattungen mit unbekanntem Ausgang, Absagen länger als 1 Stunde offen, Abbuchungen mit unbekanntem Ausgang. Eine fehlgeschlagene Erstattung wird nie automatisch wiederholt.
- **Auslöser (M2b-2):** Der Job `card-charges` (alle 5 Minuten, unabhängig von `payments_enabled`) bucht Kartenspiele ab, sobald beide Captains bereit sind und die Frist erreicht ist (48 Stunden vor Anstoß, ggf. mit Karenz); bei weniger als 48 Stunden Vorlauf sofort nach dem zweiten Bereit (zusätzlich ohne Wartezeit aus `finalConfirm`, fehlgeschlagen holt der Job nach). Er bucht auch fehlende Stripe-Gebühren nach. Sobald Abbuchungszeilen existieren, sind Beitritt, Austritt, Rauswurf, Einteilung und **jede Absage (auch durch Admin oder Job) gesperrt** (Meldung: Abbuchung begonnen, bitte Support kontaktieren; einen Admin-Pfad gibt es bis M3 nicht), ebenso Bereit ändern, Ort ändern, Teams zusammenführen und Konto löschen: Erstattung auf die Karte gibt es erst mit M3. **Betriebsrisiko:** Nach dem Anstoß verarbeitet der Job die Zeilen nicht mehr; offene Zeilen (`pending`/`requires_action`) werden je Zeile einmal mit Audit `charge.after_start` markiert (nie erneut gesendet); `failure_code` wird dabei nur gesetzt, wenn er leer ist (ein vorhandener Code wie `authentication_required` bleibt und steht im Audit-Detail `previousCode`). Dann ist die Halle gebucht, aber nicht (voll) eingezogen, und es gibt noch keine Admin-Sicht oder Auflösung (M3/009): Audit und Zeilen manuell prüfen (GO-LIVE-Betriebsrisiko). Zeilen mit unbekanntem Ausgang (`failure_code = unknown_outcome`, Status `pending`, Audit `charge.unknown_outcome`) werden nie erneut gesendet und nie automatisch auf `failed` gesetzt; sie sind manuell bzw. per M3 über die Stripe-Suche aufzulösen. Ein Idempotenz-Konflikt (`idempotency_mismatch`) setzt die Zeile auf `failed`.
- **Nachzahlfenster und Wiederabbuchen (M3c-1, Migration 0039):** Scheitert eine Abbuchung an der Karte (Stripe-Kartencode, `authentication_required`, `no_payment_method`), beginnt das Fenster: `payment_charges.grace_until` = min(2 Stunden ab dem Fehler, Anstoß minus 1 Stunde), immer gesetzt (bei höchstens 1 Stunde Restzeit ist das Ende der Fehlzeitpunkt, also kein Fenster; NULL bedeutet nie ein Kartenproblem oder Altzeile vor Migration 0039). Geprüft wird immer das effektive Ende min(`grace_until`, Anstoß minus 1 Stunde). Ändert der Spieler im Fenster seine Karte (Lobby oder Konto), wird der Platz wieder `card_ready` und sofort neu abgebucht (`retryChargesInWindow`, auch im Job `card-charges` alle 5 Minuten): neuer Versuch mit Schlüssel `charge:<Spiel>:<Nutzer>:<n>`; vorher werden die bekannten PaymentIntents per `retrieve` geprüft (erfolgreich: verbuchen statt neu senden; offen: abbrechen; `processing`: Runde auslassen). Abgeschlossene Versuche stehen in `payment_charge_attempts` (Historie), die Zeile in `payment_charges` ist immer der laufende Versuch. Der Webhook `setup_intent.succeeded` ruft `retryChargesInWindow` bewusst **synchron nach der Transaktion** auf (sofortige Abbuchung nach „Karte ändern“; kostet Stripe-Latenz im Webhook-Request, Fehler sind isoliert). Der Job `card-charges` (`runCardCharges`, nur bei eingeschaltetem Kartenmodell) ruft `retryChargesInWindow` auf und holt so nach, was der Webhook-Pfad nicht geschafft hat (Stripe-Fehler, Abbruch); Altzeilen (`grace_until` NULL) werden nie angefasst, ein veralteter Lauf bricht nie den PaymentIntent eines neueren Versuchs ab (Berechtigung und Versuchsnummer werden vor dem Netzaufruf frisch gelesen). **Bekannter Restfall:** ändert sich der Zustand zwischen dieser Prüfung und der Drehung in `rotateAttempt` (Millisekunden, z. B. paralleles Fensterende), kann eine Zeile `requires_action` mit abgebrochenem PaymentIntent stehen bleiben; sie läuft mit dem Fenster aus und wird in M3c-2 behandelt. Technische Zustände (`idempotency_mismatch`, `unknown_outcome`, `after_start`) bekommen kein Fenster und keine Spielerbenachrichtigung; Altzeilen und `idempotency_mismatch` stehen im Admin-Alarm (`getRefundAlerts`: `legacyFailed`, `idempotencyMismatches`, `duplicateSuccesses`) zur manuellen Entscheidung. **Rollback Migration 0039:** erst den Code zurückrollen, dann `drop table payment_charge_attempts; alter table payment_charges drop column grace_until, drop column current_attempt;` (rein additiv, nichts anderes hängt davon ab, solange der alte Code läuft). **`card_payments_enabled` bleibt AUS**, bis M3c-1, die 3-D-Secure-Freigabe (M3c-1c) und der Nachrücker/die Auto-Absage (M3c-2) deployt sind; ohne sie bleibt ein Spiel nach dem Fensterende hängen und `requires_action` eine Sackgasse. Hinweis für Integrationstests: `.env.local` darf keinen `STRIPE_SECRET_KEY` enthalten, sonst bucht die Gebührenbuchung ohne Nutzer und das Aufräumen scheitert am Fremdschlüssel.

- **Nachrücker von der Warteliste (M3c-2a, Migration 0040):** Läuft das Nachzahlfenster ab (effektives Ende), gibt der Job `card-charges` (`runSubstitutes`) den Platz frei: die Zeile des Zahlungsunfähigen bekommt `resolution = 'replaced'` und `slot_team_id` (sein Team), der Spieler wird als Teilnehmer **entfernt** (Wiederbeitritt zum selben Spiel gesperrt, Meldung „Dein Platz wurde vergeben“, Nachricht nur an ihn). Der Erste der Warteliste (nicht eingeteilt, Karte hinterlegt, nicht gesperrt, ohne eigene Abbuchungszeile, sortiert nach `joined_at`) rückt in das Team nach und bekommt eine neue Zeile (`slot_of` = Ursprungszeile, gleicher Anteil), die sofort über den normalen Weg abgebucht wird. Je Platz gibt es höchstens EINE aktive (`pending`) und höchstens 3 gescheiterte Nachrücker-Zeilen (`failed`/`requires_action` zählt sofort, `pending` verbraucht keinen Versuch); ein gescheiterter Nachrücker ist sofort draußen (`resolution = 'replaced'`, nur er wird benachrichtigt) und **bleibt als Teilnehmer ohne Platz** (`team_id` NULL, Karte `failed`): kein weiterer Versuch für diesen Platz (er hat schon eine Abbuchungszeile), Beitritt gesperrt; das ist so gewollt. `match_closed` (Absage, Schalter AUS) ist kein Fehlversuch. Vor dem Freigeben eines Platzes wird ein offener PaymentIntent der Zeile bei Stripe abgebrochen (`requires_action`; `processing` oder Netzfehler: Runde auslassen; schon erfolgreich: gebucht, Platz nicht vergeben). Ein Nachrücker, der mit `unknown_outcome` hängt, blockiert den Platz bis zur Klärung und steht im Admin-Alarm (`unclearedCharges`). Ebenso besetzt ein eingeteilter Nachrücker, dessen Zeile wegen Absage oder Schalter AUS geschlossen wurde (`match_closed`), den Platz weiter (kein zweiter Kandidat, sonst zwei Spieler auf einem Platz); ein ERSETZTER Nachrücker mit spätem Erfolg besetzt ihn nicht (Betrag wird gebucht und erstattet, der nächste Kandidat rückt nach). Findet die Suche nur Kandidaten, die gerade von einer anderen Transaktion gehalten werden (z. B. Kartenänderung), wird die Runde ausgelassen: die Auto-Absage ist unumkehrbar und beruht nie auf einer zufälligen Sperre. Captain und Dritte sehen nur „Kader geändert“ ohne Namen und Grund. Ist die Warteliste leer oder der Platz erschöpft (3 gescheiterte Nachrücker), wird das Spiel **automatisch abgesagt** (M3c-2b, AC-9): System-Absage ohne Akteur und ohne Rollenprüfung (`requestMatchCancel(null, …)`), alle bereits Abgebuchten werden über den Ablauf der Absage voll auf die Karte erstattet (die Stripe-Gebühr bleibt bei Soccaz). Die Abrechnung (`settleIfComplete`) läuft nur, wenn jeder vergebene Platz durch einen erfolgreichen Nachrücker besetzt ist. **Später Erfolg:** meldet Stripe für einen ersetzten Platz (oder als zweiten PaymentIntent einer Zeile) noch einen erfolgreichen PaymentIntent, wird er gebucht (`charge:<PI>`) und sofort voll erstattet (`payment_refunds.payment_intent_id`, Schlüssel `refund:<Abbuchung>[:<PI>]`), mit Admin-Alarm (`duplicateSuccesses`); der Job `card-refunds` sendet solche Einzel-Erstattungen auch ohne Absage, und eine Absage wird erst abgeschlossen, wenn ALLE Erstattungen durch sind. **Rollback Migration 0040:** erst den Code zurückrollen, dann `drop index payment_refunds_charge_idx; create unique index payment_refunds_charge_idx on payment_refunds (charge_id);` (schlägt fehl, solange es mehrere Erstattungen je Abbuchung gibt: vorher klären), `alter table payment_refunds drop column payment_intent_id; alter table payment_charges drop constraint payment_charges_resolution_check, drop constraint payment_charges_slot_of_payment_charges_id_fk, drop constraint payment_charges_slot_team_id_teams_id_fk, drop column resolution, drop column slot_of, drop column slot_team_id;` (ersetzte Plätze und Nachrücker-Zeilen verlieren dabei ihre Kennzeichnung, also vorher offene Spiele klären). Der Fremdschlüssel `slot_of` ist bewusst `NO ACTION` (Zahlungsnachweise bleiben erhalten); das Löschen eines Spiels entfernt alle seine Zeilen in einer Anweisung.
- **Anteil übernehmen, Variante B (M3c-3a, Migration 0041):** Ein eingeteilter Spieler B mit Karte übernimmt den Endanteil des Platzes von Spieler A (A ohne Karte, kein Zahlungsmittel nötig). `match_participants.covered_by_user_id` (+ `cover_mandate_text` = i18n-Schlüssel `cover.mandate.v1.entwurf`, **Entwurf, Rechtstext durch Anwalt**, + `cover_accepted_at`) hält die Übernahme (`takeOverShare`/`releaseCover` in `src/server/payments/cover.ts`); CHECK covered_by <> user_id, Einwilligung gehört zum Eintrag, **ein Platz je Übernehmer** (Teilindex), keine Kette (ein übernommener Platz hat keine Karte und kann nie Zahler sein). Möglich nur im Kartenmodell, bei offenem Spiel, **bis der Countdown „Lobby schließt“ abläuft** (`joinClosedByTime`) und solange noch keine Abbuchungszeilen existieren; im Teamspiel nur aus demselben Team, im Privatspiel jeder Eingeteilte; B nimmt die Übernahme bis dahin selbst zurück. Zur Frist (Phase A in `runCharges`) gilt sie nur, wenn B **noch eingeteilt und `card_ready`** ist und A **keine eigene Karte** hat; sonst verfällt sie (A rot, Weg wie ohne Übernahme: `cards_missing`; zahlt A inzwischen selbst, bleibt `payer_user_id` NULL). Die Zeile in `payment_charges` bleibt **die des Platzes (A)**, `payer_user_id` = B: der PaymentIntent liegt beim **Kunden von B** (Metadaten `userId` = A), Betrag und Währung wie jeder Posten (zwei Posten für B), die Erstattung (Absage, später Erfolg) geht automatisch auf diesen PaymentIntent und die Erstattungszeile gehört B. **Wessen Profil/Karte, je Stelle:** `sendCharge` (Profil des Zahlers), `applyChargeInTx` (Kundenabgleich gegen den Zahler; Metadaten gegen den Platz), `rotateAttempt`/`eligibleFilters`/`retryChargesInWindow` (Karte und Platz des Zahlers; „Karte ändern“ von B startet auch A's Versuch), Webhook `setup_intent.succeeded` (über `retryChargesInWindow({userId})` mit Zahler-Filter), `notifyChargeProblem` (Betroffener = Zahler + dessen Captain, nie A), `getCardDisplays`/`cardDisplayFor` (Flag `covered`; Dritte und A sehen den Platz neutral grün „gedeckt“ ohne Namen, nach Scheitern nur die neutrale rote Ampel), Freigabe 3-D-Secure (`getAuthorizationSecret`, `listOpenAuthorizations`, Fake: nur der Zahler, nie A), `resolveUnknown` (Kunde des Zahlers), `ensureRefundRow` (Erstattung an den Zahler), `settleIfComplete` (EIN Beleg und EINE Nachricht je Zahler über die Summe). Scheitert B bei A's Anteil, zählt A als ausgefallen (Fenster, Nachrücker wie sonst) und B bekommt dieselbe Nachzahlung. **Wiederholen bei A's Anteil (Review-Fund 1):** das Signal ist die NEUE Karte des Zahlers (sein `payment_profiles.updated_at` liegt nach dem Fehlschlag, Zahlungsmittel vorhanden), nicht sein Platzstatus; B's Platz ist nach der ersten Abbuchung `charge_pending`/`charged` und wird nie wieder `card_ready`. Ohne neue Karte wird nicht wiederholt (keine Dauerabbuchung derselben Karte). **Einwilligung endet mit dem Platz (Review-Fund 2):** Teamgleichheit gehört zur Gültigkeit (Teamspiel); Austritt, Rauswurf, Ersatz, Rück-Einteilung und neue Einteilung von A oder B löschen die Übernahme (`clearCoversInvolving`), ein Wiedereintritt braucht neue Zustimmung. **Für 3b festgehalten:** die künftige Server-Action nimmt `payerId` immer aus der Sitzung, nie aus dem Formular. **Wortlaut-Regel:** der Text hinter `cover.mandate.v1` darf nach dem Go-Live NIE verändert werden; eine neue Fassung bekommt einen neuen Schlüssel (`cover.mandate.v2`), sonst ist die gespeicherte Einwilligung (`cover_mandate_text` + `cover_accepted_at`) nicht belegbar (gleiche Regel in GO-LIVE G2-012). Der Fremdschlüssel `covered_by_user_id` ist bewusst `NO ACTION` (nicht SET NULL, sonst würde `cover_consent` verletzt); Übernahmen enden über `clearCoversInvolving`. **Die UI (Knopf, Hinweis, i18n-Text) folgt in 3b; bis dahin ist die Übernahme nur über die Server-Funktionen erreichbar.** **Rollback Migration 0041:** erst den Code zurückrollen, dann `drop index match_participants_cover_payer_idx; alter table match_participants drop constraint match_participants_cover_not_self, drop constraint match_participants_cover_consent, drop constraint match_participants_covered_by_user_id_users_id_fk, drop column covered_by_user_id, drop column cover_mandate_text, drop column cover_accepted_at; alter table payment_charges drop constraint payment_charges_payer_not_self, drop constraint payment_charges_payer_user_id_users_id_fk, drop column payer_user_id;` (rein additiv; **vorher** offene Spiele mit Zeilen `payer_user_id IS NOT NULL` klären, sonst verliert deren Erstattung den Zahler). **Oberfläche (M3c-3b):** In der Lobby steht neben einem roten Platz der Knopf "Anteil übernehmen" (nur für Mitspieler mit Karte, im Teamspiel im selben Team, einmal je Platz und je Übernehmer, nur solange keine Abbuchungszeilen existieren und die Frist nicht erreicht ist; der Server entscheidet je Betrachter, `src/server/payments/cover-view.ts`). Der Dialog zeigt den Betrag (voraussichtlich bis "Preis steht fest"), erklärt Zusatzposten, Folge bei Fehlschlag und neue Karte im Fenster und verlangt die Zustimmung zum Mandatszusatz (`cover.mandate.v1.entwurf`, **Entwurf, Rechtstext durch Anwalt**, GO-LIVE G2-012; der Wortlaut ist unveränderlich, eine neue Fassung bekommt einen neuen Schlüssel). Der Übernehmer kommt immer aus der Sitzung, die Einwilligung erzwingt der Server. Dritte sehen nur "Gedeckt" (ohne Namen), der Platz selbst "Dein Anteil wird übernommen", der Captain das Paar; Nachrichten gehen nur an Platz, Übernehmer und Captain (`cover-notify.ts`). Zurücknehmen kann nur der Übernehmer bis zur Frist.
- **Zahlungsstreit (M4a-1, Migration 0042, AC-11):** Der Kartenwebhook verarbeitet `charge.dispute.created`, `.updated`, `.funds_withdrawn`, `.funds_reinstated`, `.closed` (im Stripe-Dashboard am **neuen** Endpunkt `/api/stripe/webhook` anmelden und am alten `/api/webhooks/stripe` abmelden, sonst doppelte Meldung). Tabellen `payment_disputes` (je Stripe-Streit, `status` ohne CHECK: unbekannte Werte werden toleriert, Alarm) und `payment_dispute_entries` (je Balance-Transaction: `booked`/`parked`/`rejected`). **Gebucht wird nach den Balance-Transactions des Streits**, je Transaktion genau einmal: Abzug Soll `chargeback` / Haben `clearing` (Schlüssel `dispute:<dp>:bt:<txn>`), Rückbuchung umgekehrt, nur wenn die gebuchten Abzüge sie decken (sonst geparkt, bei abgelehntem Abzug abgelehnt), **Gebühr immer genau einmal** aus `fee` der Transaktion (Schlüssel `…:fee`, Soll `fees`; negative Gebühr bei gewonnenem Streit = Gegenbuchung; nie geschätzt, unabhängig vom Eintragsstatus). Prüfungen: `0 < Betrag <= Abbuchung`, EUR, Summe (netto) über alle Streite derselben Zahlung `<=` Abbuchung; sonst `rejected` und Alarm. Zuordnung über PaymentIntent der Abbuchung, dann Historie; ohne Treffer bleibt `charge_id`/`match_id`/`payer_user_id` leer (gebucht wird trotzdem, Alarm). Der Streit trifft den **Zahler** (`payer_user_id`). Reihenfolge-unabhängig: Upsert über `dispute_id`, Statusfelder nur bei nicht älterem `event.created` und nicht fallendem Rang (Endstatus bleibt). Fehlt die Liste der Balance-Transactions im Ereignis (oder ist ein verlorener Streit ohne Abzug darin), ruft der Webhook den Streit VOR der Transaktion bei Stripe ab (`retrieveDispute`). **Entscheide t9:** nur Markierung/Alarm, **keine automatische Sperre**; die **Absage wird nicht blockiert**: die strittige Zahlung wird nicht zusätzlich erstattet (Erstattungszeile `cancelled_dispute`, gleich beim Anlegen oder beim Eingang des Streits), alle anderen werden erstattet; Streit verloren trotz schon gesendeter Erstattung = Doppelverlust, Markierung `refund_conflict`, Abschreibung auf Konto `chargeback`, keine Rückforderung; Gewinn nach Absage: Hinweis an Admin 1 (Geld liegt bei Soccaz). Alarme (`admin.task`, höchstens einer je Streit und Grund) gehen nur an Admin 1. **Sperrreihenfolge** Spiel → Abbuchungszeile → `payment_refunds` → `payment_disputes`. **Rollback Migration 0042:** erst den Code zurückrollen (offene Streite und `parked`-Einträge vorher klären). Das Hauptbuch ist append-only: Buchungen mit Schlüssel `dispute:%` bleiben. Dann `delete from stripe_events where type like 'charge.dispute.%';` (damit ein Wiedereinspielen nicht als schon verarbeitet übersprungen wird), `drop table payment_dispute_entries; drop table payment_disputes;` und die CHECK-Regel von `payment_refunds.status` zurücksetzen (`alter table payment_refunds drop constraint payment_refunds_status_check; alter table payment_refunds add constraint payment_refunds_status_check check (status in ('pending','succeeded','failed'));`, vorher Zeilen mit `cancelled_dispute` klären). Die Admin-Oberfläche (Liste, Markierung am Spieler, Beweis-Ansicht) folgt in M4a-2; bis dahin sind Streite nur in der Tabelle und über die Alarme sichtbar.
- **DSGVO: Export und Löschung des Stripe-Kunden (M4b-1, Migration 0043, AC-16):** Der Datenexport enthält zusätzlich `card`: Stripe-Kunden-ID, Marke und letzte vier Ziffern, Mandat (Wortlaut und Zeit), Abbuchungen als Platz UND als Zahler (Rolle `own`, `payer_for_other`, `seat_covered_by_other`, ohne Namen Dritter), Erstattungen, die eigene Einwilligung zu übernommenen Anteilen und eigene Zahlungsstreite; **nicht** die Zahlungsmittel-ID. **Löschung:** `deleteAccount` legt in DERSELBEN Transaktion wie die Anonymisierung einen Auftrag in `payment_erasure_tasks` an (die Kunden-ID steht danach nur noch dort) und löscht `payment_profiles` und `payment_setup_intents` (Mandat) des Nutzers; die Transaktion ruft Stripe nie auf. Ein **offener Zahlungsstreit** (inkl. unbekannter Status) hält die Löschung auf (Beweismittel; **[FRAGE-RECHT]**, siehe `docs/design/m4-plan.md`). Der Job `card-charges` (alle 5 Minuten, auch bei ausgeschaltetem Kartenmodell) ruft `runErasureTasks` auf: Auftrag beanspruchen (`FOR UPDATE SKIP LOCKED`, Lease 5 Minuten, der Versuch wird schon beim Beanspruchen gezählt), `deleteCustomer` bei Stripe (Netz, nie in einer Transaktion; „Kunde existiert nicht (mehr)“ = Erfolg, ein Absturz nach dem Stripe-Erfolg ist harmlos), bei Erfolg `done` und Kunden-ID NULL. Zustände `pending` → `claimed` → `done` | `failed`. Fehler: Backoff 1 h, 6 h, 24 h, danach täglich; nach **10 Versuchen** `failed` und **ein** Alarm an Admin 1 (Kunden im Stripe-Dashboard von Hand löschen; ohne Kunden-ID im Alarm). Ist Stripe nicht konfiguriert, wartet der Auftrag, ohne einen Versuch zu verbrauchen. **[ANNAHME]** Stripe behält Transaktionsdaten nach eigenen Aufbewahrungspflichten (Hinweis in der Datenschutzerklärung; vor Go-live bestätigen). **Bekannte Lücke:** trifft ein Zahlungsstreit NACH der Kontolöschung ein, wird er über den PaymentIntent zugeordnet und gebucht (Zahler ist die anonymisierte Nutzerzeile), Mandat und Profil fehlen als Beweis; die Beweis-Ansicht zeigt „Mandat nach der Kontolöschung entfernt“ (**[FRAGE-RECHT]**). **Rollback Migration 0043 (Reihenfolge):** (1) offene Aufträge abarbeiten (Job laufen lassen oder die Kunden im Stripe-Dashboard von Hand löschen; `pending`, `claimed` und `failed` müssen leer sein, sonst bleibt ein Stripe-Kunde bestehen), (2) Code zurückrollen, (3) `drop table payment_erasure_tasks;`. **Sperren in `deleteAccount` (Review M4b-1):** (1) derselbe Advisory-Lock wie `createCardSetup` (`card-setup:<Nutzer>`, nie warten): ist gerade eine Karteneinrichtung dran, kommt „Deine Karte wird gerade eingerichtet“; `createCardSetup` prüft Nutzer/gesperrt nach dem Lock noch einmal, damit nach der Löschung kein neuer Stripe-Kunde mit der alten E-Mail entsteht. (2) Reihenfolge Spiel → Abbuchungszeile → `payment_refunds` → Nutzer (alle Zeilen des Nutzers als Platz UND als Zahler, alle betroffenen Spiele zuerst, sortiert); danach setup_intents → Profil (wie der Webhook `setup_intent.succeeded`). (3) Eine **laufende** Zahlung hält die Löschung auf: Abbuchungszeile `pending` (als Platz oder Zahler) oder Erstattung `pending` in irgendeinem Spiel (sonst ginge die Zeile mit `no_payment_method` auf `failed`, bei einem Zahler zulasten des Platzes eines Dritten). Der Job schreibt `done` und das Audit in EINER Transaktion; ein Audit-Fehler setzt den Auftrag nicht auf `pending` zurück (er bleibt beansprucht, der nächste Lauf nach der Lease beendet ihn).
- **3-D-Secure-Freigabe (M3c-1c, AC-7, keine Migration):** Verlangt die Bank für einen Versuch eine Freigabe (`requires_action`, Code `authentication_required`), sieht der Betroffene in der Lobby den Knopf „Zahlung freigeben“ (im Konto unter „Offene Freigaben“ nur ein Link). Die Server-Aktion `createAuthorizationAction` liefert NUR ihm das `clientSecret` des laufenden Versuchs (Bedingungen: Kartenmodell AN, Spiel offen, Zeile `requires_action`, Fenster läuft; bei Stripe nochmals `requires_action` mit passendem Betrag/EUR/Kunde; höchstens 10 Herausgaben je Nutzer und Stunde; Audit `charge.authorization_requested` ohne Secret). Stripe.js (`handleNextAction`) schließt die Prüfung im Browser ab; das Ergebnis dort bucht NICHTS, gebucht wird allein über den Webhook (`payment_intent.succeeded` / `payment_failed` → `applyChargeInTx`). Scheitert die Prüfung, wird die Zeile `failed` im Fenster („Karte ändern“, Wiederabbuchen); läuft das Fenster ab, wird ein offener PaymentIntent abgebrochen und der Platz vergeben (M3c-2). Content-Security-Policy erlaubt `js.stripe.com` und `hooks.stripe.com` bereits (`src/lib/csp.ts`). Das Secret steht nur in der POST-Antwort der Server-Aktion (nie in Seite, RSC-Payload, URL, Log). Tests/CI: mit `PAYMENTS_FAKE=1` gibt es stattdessen zwei Test-Knöpfe, die ein signiertes Fake-Webhook-Ereignis auslösen (derselbe Weg). Ohne diese Freigabe wäre `requires_action` eine Sackgasse: `card_payments_enabled` bleibt AUS, bis M3c-1, M3c-1c und M3c-2 deployt sind.
- **Nachrücker: Alter und Einrichtung (R-T183):** Kandidaten der Warteliste brauchen `onboarded_at` UND `age_confirmed_at` (Alterspruefung beim Onboarding, `MIN_AGE`) zusätzlich zum Beitritts-Gate. Plattform-Mitarbeiter (`ensureStaffOnboarded`: Admin, Finanzen, Buchung, Moderation) bekommen `onboarded_at` ohne Alterspruefung, haben aber kein `age_confirmed_at` und spielen nicht mit; sie sind nie Nachrücker. Der Nachrücker rückt in das Team des ersetzten Platzes (`slot_team_id`, Heim oder Auswärts); die neutrale Nachricht „Kader geändert“ geht an die Captains genau dieses Teams.
- **Konto-Löschung bei laufender Abbuchung (DSGVO Art. 17):** Hat ein offenes Spiel (`lobby`/`confirmed`) des Nutzers Abbuchungszeilen, lehnt `deleteAccount` ab ("Bitte wende dich an den Support; die Löschung wird nach Klärung der Abbuchung durchgeführt"). Die Zeilen bleiben bis M3 offen, das Spiel wird nie automatisch abgesagt; die Löschung läuft deshalb **manuell über den Support**, sobald die Abbuchung geklärt ist (Zeilen terminal oder erstattet). Zahlungsnachweise (Belege, Hauptbuch, Abbuchungszeilen) bleiben nach Handels- und Steuerrecht aufbewahrt, die Löschung anonymisiert nur personenbezogene Angaben (Frist: unverzüglich nach Klärung, spätestens innerhalb eines Monats). Nur relevant, solange `card_payments_enabled` AN ist; der Schalter geht in Produktion erst nach M3/M4 an.
- **Bekannter Rest-Zyklus (sehr eng):** `mergeTeams` sperrt Team -> Spiele, `deleteAccount` Spiel -> Team (archiviert das Team, wenn der Löschende dessen einziger Admin ohne Mitglieder ist). Treffen beide im selben Moment dasselbe Team, bricht Postgres eine der Transaktionen ab (Deadlock-Erkennung); nichts wird beschädigt, die Aktion lässt sich wiederholen.
- `PAYMENTS_FAKE` darf in Staging und Produktion nie gesetzt sein (nur Tests/CI). In Produktion mit `PAYMENTS_FAKE=1` bricht die Kartenzahlung mit einem harten Fehler ab. Ohne Stripe-Schlüssel und ohne `PAYMENTS_FAKE` ist die Kartenzahlung ausgeschaltet (Webhook antwortet 503).

Hinweise: Das Buchungsjournal ist unveränderlich (Datenbank-Trigger). Korrekturen sind Gegenbuchungen. Die Zahlungsgebühr wird beim Verbuchen **geschätzt** (Einstellung oben); die echten Gebühren stehen im Stripe-Dashboard und sollten monatlich abgeglichen werden.

### Lokale Entwicklung mit Stripe-Testmodus (Kurzfassung)

Die Einzelheiten stehen oben; hier die Reihenfolge für Worker-Worktrees. Nur Namen, nie Werte.

1. **Schlüssel (Testmodus, nie Live):** `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` und `STRIPE_CARD_WEBHOOK_SECRET` stehen in der `.env.local` des Nutzers. Testschlüssel beginnen mit `sk_test_` bzw. `pk_test_`; ein Live-Schlüssel gehört in keine `.env.local`.
2. **Worktrees:** `scripts/worktree.mjs create` kopiert die `.env.local` aus SoccaV2 nur beim Anlegen und ändert dabei nur `DATABASE_URL` und `PORT`. Änderungen an der Haupt-`.env.local` (z. B. neue Stripe-Schlüssel) kommen in bestehende Worktrees nicht an: dort selbst nachtragen oder den Worktree neu anlegen. Agenten lesen und geben `.env*` nie aus.
3. **Webhook lokal:** `stripe listen --forward-to localhost:<Port>/api/stripe/webhook` mit dem Port des Servers (Worker 3101 bis 3104, Haupt-Instanz 3100). Das Signaturgeheimnis (`whsec_...`) aus der Ausgabe von `stripe listen` ist das Test-Webhook-Secret und kommt als `STRIPE_CARD_WEBHOOK_SECRET` in die `.env.local` des jeweiligen Worktrees, nicht in andere.
4. **`PAYMENTS_FAKE=1`** nur für Tests und CI (Fake-Anbieter ohne Stripe). In Produktion und Staging nie setzen: Staging läuft mit `NODE_ENV=production`; der Code verweigert `PAYMENTS_FAKE=1` nur bei `NODE_ENV=production` (`src/server/payments/provider.ts` wirft einen harten Fehler), die Regel für Staging ist also eine Betriebsregel und zugleich durch den Produktions-Build abgesichert. Ist `STRIPE_SECRET_KEY` gesetzt, wählt der Code Stripe statt des Fake-Anbieters; die Integrationstests brauchen den Fake-Anbieter und werden deshalb mit leerem Schlüssel gestartet (`STRIPE_SECRET_KEY= npm run test:integration`; die `.env.local` überschreibt eine schon gesetzte, auch leere Variable nicht). `STRIPE_WEBHOOK_SECRET` setzt die CI für die Tests auf einen Testwert (`.github/workflows/ci.yml`); lokal ist dafür nichts zu tun, die Tests, die ein Webhook-Geheimnis brauchen, setzen es selbst (z. B. `tests/integration/card-setup.test.ts`).
5. **`card_payments_enabled` umlegen:** nur ohne offene bezahlte Spiele (GO-LIVE G8-012; die Konto-Löschung bei laufender Abbuchung läuft nur über den Support), und in Produktion erst, wenn M3c-1 (Fenster und Wiederabbuchen), M3c-1c (3-D-Secure-Freigabe) UND M3c-2 (Nachrücker, automatische Absage) gemergt und deployt sind (GO-LIVE G8-012, G9-012).

## Admin 1 festlegen (Vertrag 009 M1, nur Betreiber)
Admin 1 (Seitenbetreiber) ist das eine Konto mit `users.role = 'admin'` UND `users.is_owner = true`; die Datenbank erlaubt höchstens eines. Es entsteht nie von selbst: Die Migration setzt niemanden, das macht dieser Schritt.

**Reihenfolge beim Einspielen:** 1. Migration (`docker compose run --rm app node scripts/migrate.mjs` bzw. der übliche Update-Ablauf) → 2. neuen Code ausrollen (alle Plattform-Prüfungen kennen Admin 1, E1b) → 3. Admin 1 festlegen → 4. erst danach Alarme nur an Admin 1 (E2). Vor Schritt 3 verhält sich alles wie bisher, weil Admin 1 weiter die Rolle `admin` trägt.

**Festlegen** (Konto muss sich einmal angemeldet haben; Datenbank aus `DATABASE_URL` der Umgebung):
```
node scripts/set-owner.mjs <email>          # Trockenlauf: zeigt nur Host, Port und Datenbankname
node scripts/set-owner.mjs <email> --yes    # führt aus
```
Das Skript ist idempotent (zweiter Aufruf für dasselbe Konto: „Unverändert“), bricht ab, wenn ein ANDERES Konto schon Admin 1 ist, das Konto fehlt oder gesperrt ist, und schreibt einen Protokolleintrag `user.owner_set` ohne Akteur. Es zeigt nie Benutzer oder Passwort der Datenbank.

**Ein anderes Konto soll Admin 1 werden (Übergabe):** zuerst das alte Konto freigeben (`update users set is_owner = false where email = '<alt>'`), dann das Skript für das neue Konto. Ohne Admin 1 gehen die Alarme ab E2 nicht an Dritte (nur Server-Log), deshalb die Lücke kurz halten.

**Rückgängig (Rollback):** Code auf den vorherigen Stand zurück; Admin 1 lässt sich ohne Datenverlust abgeben (`is_owner = false`). Die Spalte `is_owner` und der Teilindex `users_one_owner` bleiben ungenutzt stehen (Datenbankänderungen sind nur vorwärts, vorher sichern).

**Prüfung der Migration** (lokal, Wegwerf-Datenbanken, löscht sie danach): `node --env-file=.env.local scripts/migrate-check.mjs` (frische Datenbank mit allen Migrationen in einem Lauf und bestehende Datenbank mit Daten).
